## ۱. دکمه‌های NFC — اشتباه از من بود

گفتید «طوسی، اندازه و رنگ نامناسب، کارایی کم». **هر سه درست بود و یک علت داشت.**

من نوشته بودم `className="seg"` و `seg-on`. **هیچ‌کدام از این کلاس‌ها در CSS
برنامه وجود ندارند.** کلاس واقعی `.segmented` با `.active` است به‌علاوهٔ یک
`<SegIndicator>`.

یعنی آن دکمه‌ها **اصلاً استایل نداشتند** — نه پس‌زمینه، نه ارتفاع، نه حالت فعال.
«بد طراحی شده» نبودند؛ **بی‌استایل** بودند.

بدترین بخش: اسم کلاس غلط **هیچ خطایی نمی‌دهد**. CSS چیزی به‌نام «سلکتور ناشناخته»
ندارد و build هم اهمیتی نمی‌دهد. تست شمارهٔ ۲۶ ما دقیقاً برای همین نوشته شده بود،
ولی فقط فایل‌هایی را بررسی می‌کرد که *از قبل* `className="segmented"` داشتند — پس
کلاس ساختگی من از کنارش رد شد.

**اصلاح شد:** حالا یک تست، فهرست کلاس‌های تعریف‌شده را از خود فایل CSS می‌خواند و
هر کلاس `seg*` تعریف‌نشده را رد می‌کند. تست کردم که واقعاً کار می‌کند — باگ را
عمداً برگرداندم و تست گیر داد.

## ۲. «کارایی کم» — این هم درست بود، و بدتر

بخش «دریافت» فقط لینک را به‌صورت **متن** چاپ می‌کرد تا طرف مقابل ۴۲ کاراکتر را از
روی صفحه بخواند و تایپ کند — **دقیقاً همان کاری که این قابلیت برای حذفش ساخته شده**
و همان اشتباهی که انتقال بلاکچینی برگشت‌پذیرش نیست.

در همین برنامه از قبل **مولد QR** (در ReceiveSheet) و **اسکنر QR** (با
BarcodeDetector داخلی خود WebView) وجود داشت. هر دو بلااستفاده مانده بودند، در حالی
که به کاربران آیفون — که اصلاً NFC ندارند — می‌گفتم «از کد استفاده کنید»، کدی که
هرگز نمایش نمی‌دادم.

**حالا:**
- طرف دریافت‌کننده یک **QR واقعی و قابل اسکن** نشان می‌دهد (روی زمینهٔ سفید، چون
  اسکنرها به مربع‌های تیره روی زمینهٔ روشن نیاز دارند)
- طرف پرداخت‌کننده **دوربین اسکنر واقعی** را باز می‌کند
- دکمهٔ **کپی** هم اضافه شد
- **اسکن اول است، NFC دوم** — چون NFC فقط روی ۶٪ مرورگرها و هیچ آیفونی کار می‌کند

## ۳. کارمزد P2P — با قوی‌ترین مدرک ممکن

خواستید مطمئن شوم. فقط به فیلد JSON اکتفا نکردم؛ **خود تراکنشی که کاربر امضا
می‌کند را باز کردم و خواندم.**

درخواست زنده با گیرنده‌ای که **عمداً با پرداخت‌کننده فرق داشت**:

```
گیرندهٔ سواپ            : 0x1111…1111
پرداخت‌کننده             : 0xd8dA…6045
اکشن انتقال کارمزد a9059cbb
  مقصد                  : 0xaf5ce154cefd22da5bd1d0a54479e81963a224d6  ← کیف ما
  فیلد bps (0x46)       : ۷۰
```

یعنی در **یک تراکنش امضاشده**: طرف مقابل توکن خریداری‌شده را می‌گیرد و **ما ۰٫۷٪
را می‌گیریم**. هر دو تأیید شد.

و اگر هر دو طرف همان توکن را بخواهند، کد می‌گوید «این انتقال است» و **کارمزد
نمی‌گیرد** — سواپی انجام نشده که بابتش پول بگیریم.

## ۴. کارهای بی‌هزینه برای موارد باقی‌مانده

خواستید: «روش‌های جامانده را با کارمزد صفر بزن تا بعداً که پول آمد هزینه کنیم».

**هر پنج مورد را بررسی کردم. خبر خوب: کد همه‌شان از قبل کامل است.**

هر کدام فقط **یک متغیر محیطی** می‌خوانند و خودشان روشن می‌شوند. هیچ کار
برنامه‌نویسی باقی نمانده که بشود جلو انداخت:

| مورد | متغیر | وضعیت کد |
|---|---|---|
| GMX | `VITE_GMX_REF_CODE` | ✅ بازنویس لینک، اعتبارسنجی کد، UI — همه آماده |
| THORName | `THOR_NAME` | ✅ `affiliateFor()` خودش memo کوتاه را انتخاب می‌کند |
| صندوق Morpho | `VITE_FBT_VAULT_ADDRESS` | ✅ کل صفحه آماده، بدون آدرس چیزی نشان نمی‌دهد |
| Trezor | `VITE_AFFILIATE_TREZOR` | ✅ کارت آماده، بدون کد لینک ساده می‌دهد |
| ژوپیتر | `JUP_REFERRAL_ACCOUNT` | ✅ ولی دیگر لازم نیست — OpenOcean همان ۰٫۷٪ را رایگان می‌دهد |

### پس چه کار **می‌شد** کرد؟

چیزی که واقعاً کم بود، **راهی برای تأیید این حرف** بود. شما با گوشی کار می‌کنید و
کد نمی‌خوانید، و من برای پنج قابلیت مختلف گفته‌ام «آماده است، فقط متغیر را ست کن».
آن ادعا تا امروز **قابل بررسی نبود** — و این دقیقاً همان شکل باگ «وصل به هیچ» است
که سه بار در این پروژه اتفاق افتاده.

**ساختم:** یک آدرس که از گوشی باز می‌شود:

🔗 **`https://fbtswap.ir/api/revenue/readiness`**

نتیجهٔ زندهٔ همین الان:

```json
{ "live": 7, "total": 13, "costToActivateAll": 35.02,
  "allRemainingAreCodeComplete": true }
```

**۷ خط درآمدی زنده. ۳۵٫۰۲ دلار برای بقیه. و همهٔ باقی‌مانده‌ها کد کامل دارند.**

`live` و `ready` عمداً جدا هستند: `ready` یعنی کد آماده است، `live` یعنی الان پول
می‌گیریم. اگر یکی‌شان کرد `ready: false`، **آن یکی کار برنامه‌نویسی است نه خرید** —
و آن وقت کار من است، نه شما.

هیچ مقداری را نشان نمی‌دهد، فقط `true/false`.
