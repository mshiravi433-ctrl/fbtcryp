# متغیرهای محیطی — هر کدام را از کجا بیاورم

> **مرجع کامل: [`.env.example`](../.env.example)**
>
> این سند راهنمای گام‌به‌گامِ راه‌اندازی نوتیفیکیشن است. اگر دنبال **فهرست
> کامل هر متغیری که در کد خوانده می‌شود** هستید — با یک خط توضیح فارسی، مقدار
> پیش‌فرض واقعیِ خوانده‌شده از خود کد، و اینکه خالی گذاشتنش دقیقاً کدام قابلیت
> را خاموش می‌کند — به `.env.example` بروید. آنجا در چهار دسته مرتب شده است:
>
> | دسته | یعنی چه |
> |---|---|
> | **۱ — الزامی برای فعال‌سازی** | بدون اینها رجیستری اکوسیستم اصلاً بالا نمی‌آید |
> | **۲ — الزامی برای این قابلیت خاص** | هرکدام دقیقاً یک قابلیت را روشن می‌کند |
> | **۳ — اختیاری با مقدار پیش‌فرض** | خالی گذاشتنشان چیزی را نمی‌شکند |
> | **۴ — هرگز در Vercel نگذارید** | فقط محلی؛ گذاشتنشان در پنل وب یعنی سپردن دارایی |
>
> **اعتبارسنجی خودکار دستهٔ ۱:**
>
> ```bash
> node scripts/validate-activation-env.mjs
> ```
>
> این اسکریپت `BLOB_READ_WRITE_TOKEN` و `ECOSYSTEM_CERTIFIERS` را چک می‌کند،
> یک گزارش JSON با شمای `fbt.activation-env-validation.v1` چاپ می‌کند، و اگر
> چیزی کم باشد با کد خروج ۱ تمام می‌شود. **هیچ‌وقت مقدار واقعی متغیرها را چاپ
> نمی‌کند** — فقط می‌گوید تنظیم شده یا نه، و فرمتش درست است یا نه.

## متغیرهایی که نبودشان باعث توقف می‌شود

بیشتر متغیرهای این پروژه fallback دارند: نبودشان فقط یک قابلیت را خاموش
می‌کند و اپ صادقانه می‌گوید در دسترس نیست. اما چند متغیر هستند که کد بدون
آنها **متوقف می‌شود**. هر سه فقط در اسکریپت‌های محلی‌اند، نه در خودِ اپ یا
سرور — یعنی هیچ‌کدام نمی‌توانند سایت را از کار بیندازند:

| متغیر | کجا | چه اتفاقی می‌افتد |
|---|---|---|
| `RPC_URL` | `scripts/deploy-all.mjs` | خالی یا غیر https → `Set RPC_URL to an HTTPS RPC endpoint.` و خروج ۱ |
| `CHAIN_ID` | `scripts/deploy-all.mjs` | خالی یا غیرعدد → `CHAIN_ID must be a positive integer.` و خروج ۱ |
| `DEPLOYER_PRIVATE_KEY` یا `DEPLOYER_KMS_KEY_ID` | `scripts/deploy-all.mjs`، `scripts/lib/kmsAdapter.mjs`، `scripts/deploy-feerouter.mjs` | اگر **هیچ‌کدام** نباشد → `No signer configured…` (پرتاب خطا) یا خروج ۱ |

این توقف‌ها عمدی و درست‌اند: یک اسکریپت دیپلوی که بدون کلید یا بدون شبکه
«ادامه» بدهد، بدترین حالت ممکن است.

## بخش ۱ — سه مقدار اول را خودت بساز

### چرا از سایت‌های «VAPID generator» استفاده نکن

سایت‌های زیادی پیشنهاد می‌دهند این کلیدها را برایت بسازند. **هیچ‌وقت از آن‌ها استفاده نکن.**
کلید خصوصی همان چیزی است که ثابت می‌کند نوتیفیکیشن از سرور تو آمده. هرکس آن را
داشته باشد می‌تواند به همهٔ کاربران تو، از طرف تو، نوتیفیکیشن بفرستد. سایتی که
آن را می‌سازد، طبق تعریف آن را دیده است.

اسکریپتی که نوشتم فقط از کتابخانهٔ داخلی خود Node استفاده می‌کند و **به هیچ
شبکه‌ای وصل نمی‌شود**.

### اجرا

اگر کامپیوتر داری:

```bash
git clone https://github.com/mshiravi433-ctrl/fbtcryp
cd fbtcryp
node scripts/make-keys.mjs
```

اگر فقط گوشی داری، در ترموکس:

```bash

cd ~ && curl -O https://raw.githubusercontent.com/mshiravi433-ctrl/fbtcryp/arena/019fa8cd-fbtcryp/scripts/make-keys.mjs

```

خروجی سه مقدار می‌دهد، هر کدام با نام خودش. همان‌ها را کپی کن.

> ⚠️ خروجی را در چت، اسکرین‌شات یا issue نفرست. اگر فرستادی، اسکریپت را
> دوباره اجرا کن و هر دو مقدار مخفی را عوض کن.

## بخش ۲ — سه مقدار فایربیس

### گام ۱: کلید تازه بساز (کلید قبلی سوخته)

کلید قبلی را در چت فرستادی، پس دیگر امن نیست. اول همان را حذف کن:

<https://console.cloud.google.com/iam-admin/serviceaccounts?project=fbtswap-36b13>

۱. روی `firebase-adminsdk-fbsvc@fbtswap-36b13.iam.gserviceaccount.com` کلیک کن
۲. تب **KEYS**
۳. کلیدی که شناسه‌اش با `dd3e2f8a` شروع می‌شود → آیکون سطل زباله → **DELETE**
۴. **ADD KEY** → **Create new key** → نوع **JSON** → **CREATE**

یک فایل `.json` دانلود می‌شود. آن فایل را باز کن (با هر ویرایشگر متنی).

### گام ۲: سه مقدار را از داخل فایل بردار

داخل فایل چیزی شبیه این می‌بینی:

```json
{
  "type": "service_account",
  "project_id": "fbtswap-36b13",
  "private_key_id": "...",
  "private_key": "-----BEGIN PRIVATE KEY-----\nMIIEvQ...\n-----END PRIVATE KEY-----\n",
  "client_email": "firebase-adminsdk-fbsvc@fbtswap-36b13.iam.gserviceaccount.com",
  ...
}
```

سه مقدار را از همان‌جا بردار:

| متغیر Vercel | کدام فیلد JSON |
|---|---|
| `FIREBASE_PROJECT_ID` | مقدار `project_id` → `fbtswap-36b13` |
| `FIREBASE_CLIENT_EMAIL` | مقدار `client_email` |
| `FIREBASE_PRIVATE_KEY` | مقدار `private_key` |

### ⚠️ مهم‌ترین نکتهٔ کل این سند

مقدار `private_key` را **دقیقاً همان‌طور که هست** کپی کن، شامل:

- `-----BEGIN PRIVATE KEY-----` در ابتدا
- همهٔ دنباله‌های `\n` وسط متن
- `-----END PRIVATE KEY-----\n` در انتها

**دنباله‌های `\n` را پاک نکن و به خط جدید تبدیل نکن.**

چرا: کادر متنی Vercel نمی‌گذارد خط واقعی تایپ کنی، برای همین کلید با `\n`
نوشته می‌شود و سرور خودش آن‌ها را به خط واقعی برمی‌گرداند. اگر خودت پاکشان
کنی، کلید خراب می‌شود و خطایی که می‌گیری `invalid_grant` است — که هیچ اشاره‌ای
به علت واقعی ندارد. این شایع‌ترین دلیل شکست راه‌اندازی FCM است و من با یک کلید
آزمایشی تستش کردم.

فقط علامت‌های نقل‌قول `"` ابتدا و انتها را نگذار.

## بخش ۳ — وارد کردن در Vercel

برای **هر شش** مقدار، این کار را تکرار کن:

۱. **Vercel → پروژه → Settings → Environment Variables**
۲. **Key**: نام متغیر (مثلاً `VAPID_PRIVATE_KEY`)
۳. **Value**: مقدار
۴. **Environments**: هر سه تیک را بزن — **Production، Preview، Development**
۵. **Save**

### دو اشتباه که همه مرتکب می‌شوند

**۱. پیشوند `VITE_` روی مقدار مخفی نزن.**
هرچیزی که با `VITE_` شروع شود، داخل فایل جاوااسکریپتی که **هر کاربر دانلود
می‌کند** کامپایل می‌شود. یعنی «مخفی» با پیشوند `VITE_` منتشر شده است، نه ذخیره.
فقط `VITE_VAPID_PUBLIC_KEY` این پیشوند را دارد، چون واقعاً عمومی است.

**۲. بعد از ذخیره حتماً Redeploy کن.**
Vercel متغیرها را **در زمان بیلد** داخل کد می‌گذارد. دیپلویِ فعلی همان مقادیر
قدیمی را نگه می‌دارد، پس به نظر می‌رسد تغییرت هیچ اثری نداشته.

مسیر: تب **Deployments** → روی آخرین دیپلوی → منوی سه‌نقطه → **Redeploy**

## بخش ۴ — چک کن که واقعاً کار می‌کند

بعد از Redeploy، این آدرس را در مرورگر باز کن:

```
https://<اسم-اپ-تو>.vercel.app/api/cron/status
```

جواب سالم چنین چیزی است:

```json
{
  "web":  { "configured": true, "subscribers": 0, "missing": [] },
  "fcm":  { "configured": true, "devices": 0, "missing": [] },
  "cronSecretSet": true,
  "durableStorage": true,
  "canSend": false
}
```

نکات خواندن این خروجی:

- `"missing": []` یعنی هیچ متغیری کم نیست. اگر چیزی داخلش بود، **دقیقاً نام
  همان متغیر** را می‌گوید که هنوز تنظیم نشده.
- `"configured": true` یعنی کلیدها رسیده‌اند.
- `"canSend": false` وقتی `subscribers` و `devices` صفرند **طبیعی است** —
  یعنی هنوز هیچ دستگاهی نوتیفیکیشن را روشن نکرده. اپ را باز کن، نوتیفیکیشن را
  فعال کن، دوباره این صفحه را ببین: عدد باید ۱ شود.

این صفحه هیچ‌وقت **مقدار** کلیدها را نشان نمی‌دهد، فقط می‌گوید هست یا نیست.

### تست فرستادن واقعی

```
https://<اسم-اپ-تو>.vercel.app/api/cron/daily
```

بدون رمز باید `{"error":"UNAUTHORIZED"}` بدهد — همین درست است و یعنی محافظ کار
می‌کند. برای تست واقعی باید هدر `Authorization: Bearer <CRON_SECRET>` بفرستی.

## بخش ۵ — دو متغیر دیگر که یادت نرود

این دو ربطی به پوش ندارند ولی **علت کار نکردن WalletConnect و ورود با اثر
انگشت** هستند:

| متغیر | مقدار |
|---|---|
| `VITE_API_BASE` | `https://<اسم-اپ-تو>.vercel.app/api` |
| `VITE_PUBLIC_URL` | `https://<اسم-اپ-تو>.vercel.app` |

چرا لازم‌اند: اپ اندروید صفحاتش را از `https://localhost` بارگذاری می‌کند. متامسک
یک **اپ جداگانه** است — آن آدرس برایش یعنی گوشی خودِ متامسک، جایی که هیچ سروری
نیست. برای همین درخواست را رد می‌کند. WebAuthn (اثر انگشت) هم روی `localhost`
کار نمی‌کند چون مرورگر آن را دامنهٔ معتبر نمی‌داند.

تا این دو تنظیم نشوند، آن دو قابلیت کار نخواهند کرد — هرچقدر هم کدشان درست باشد.

## خلاصه در یک نگاه

```
□ کلید قدیمی فایربیس را Delete کن
□ کلید JSON تازه بساز و دانلود کن
□ node make-keys.mjs را اجرا کن → ۳ مقدار
□ ۶ متغیر را در Vercel وارد کن (هر سه محیط تیک بخورد)
□ VITE_API_BASE و VITE_PUBLIC_URL را هم اضافه کن
□ Redeploy
□ /api/cron/status را باز کن → همهٔ missing ها خالی باشد
□ اپ را باز کن، نوتیفیکیشن را روشن کن → subscribers باید ۱ شود
```

## متغیرهای اختیاری رجیستری اکوسیستم

| متغیر | برای چه | اگر تنظیم نشود |
|---|---|---|
| `BLOB_READ_WRITE_TOKEN` | ذخیره‌سازی پایدار کاتالوگ ایجنت/استراتژی، گواهی‌ها، کلیدهای API | نوشتن با ۵۰۳ رد می‌شود و خواندن `dataStatus: "unavailable"` می‌دهد |
| `ECOSYSTEM_CERTIFIERS` | فهرست بازبین‌های مجاز به صدور گواهی، به شکل `آیدی‌تلگرام:برچسب` و جداشده با کاما — مثلاً `12345:FBT Review` | هیچ‌کس نمی‌تواند گواهی بدهد، پس هیچ لیستینگی منتشر نمی‌شود و کاتالوگ عمومی خالی می‌ماند |

هر دو عمداً fail-closed هستند: نبودشان باعث نمایش دادهٔ تأییدنشده به‌عنوان
تأییدشده نمی‌شود، فقط کاتالوگ را خالی نگه می‌دارد. جزئیات در
`docs/ECOSYSTEM-REGISTRY-FA.md`.

بررسی خودکار همین دو متغیر:

```bash
node scripts/validate-activation-env.mjs
```

## بقیهٔ متغیرها کجا مستند شده‌اند

این سند فقط هشت متغیرِ راه‌اندازی اولیه را پوشش می‌دهد. مجموع متغیرهایی که
در کد این پروژه خوانده می‌شوند بیش از **۱۷۰** تاست: کلیدهای دادهٔ بازار،
مسیرهای سواپ و بریج، کلیدهای امضای پروتکل Intent، آدرس‌های دریافت کارمزد،
محدودیت نرخ و تایم‌اوت‌ها.

همه‌شان در [`.env.example`](../.env.example) هستند، دسته‌بندی‌شده، و برای هر
کدام سه چیز نوشته شده:

1. یک خط توضیح فارسی که می‌گوید این متغیر چه کاری می‌کند
2. مقدار پیش‌فرض واقعی، همان‌طور که در کد خوانده می‌شود، با نام فایل
3. اینکه اگر خالی بماند **دقیقاً کدام قابلیت خاموش می‌شود**

در آن فایل هیچ مقدار واقعی و هیچ رمزی نیست — فقط placeholder.

### قانونی که بیشتر از همه اشتباه می‌شود

هر متغیری که با `VITE_` شروع شود، در زمان build داخل فایل جاوااسکریپتی که
**هر کاربر دانلود می‌کند** کامپایل می‌شود. یعنی عمومی است، نه مخفی. گذاشتن
پیشوند `VITE_` روی یک رمز، آن رمز را **منتشر** می‌کند، نه ذخیره.

تنها استثنای آگاهانه `VITE_GEMINI_API_KEY` است: قابل استخراج از APK بودنش
پذیرفته شده و راه‌حلش «Android API key restriction» خود گوگل است. اگر خالی
بگذارید، اپ از مسیر امن سرور استفاده می‌کند.

## اپراتور سندباکس (فقط توسعه/پیش‌نمایش)

صفحهٔ Settings → Intent AI Activation به‌صورت fail-closed کار می‌کند: فعال‌سازی
فقط با شواهد عملیاتیِ تأییدشده داده می‌شود و در یک دپلوی تازه هیچ‌چیز پیکربندی
نشده است. برای اینکه دمو و توسعه همان مسیر واقعی را طی کنند، سرور یک **اپراتور
سندباکس داخلی** دارد:

- `server/intentSandboxEvidence.js` — ۲۱ نوع شواهد را با کلید Ed25519 خودش
  خود-تصدیق می‌کند (digest هر نوع، SHA-256 واقعیِ فایل‌های پیاده‌ساز آن نوع است)
  و هر رکورد از همان دروازهٔ اعتبارسنجی مسیر HTTP عبور می‌کند. مبدأ همیشه
  `sandbox-operator-self-attested` است تا هیچ سطحی آن را با بازبینی بیرونی اشتباه
  نگیرد.
- `server/intentSandboxOps.js` — کلید هماهنگ‌کننده و توکن بستن مزایده را هم محلی
  می‌سازد تا جریان بستن امضاشده در dev هم کامل اجرا شود.

دروازه: `INTENT_AI_SANDBOX_EVIDENCE` — پیش‌فرض در dev/preview روشن، در
production خاموش؛ `NODE_ENV=test` هم همیشه خاموش می‌کند تا تست‌های fail-closed
معتبر بمانند. شواهد سندباکس هرگز جای شواهد بازبینی‌شدهٔ بیرونی را نمی‌گیرد:
همین که رکورد واقعی (از `INTENT_OPERATIONAL_EVIDENCE` یا مسیر دو-اپراتوره) برسد،
بر رکورد سندباکسِ همان نوع غلبه می‌کند.
