## کاری که تو باید بکنی

**برای اینکه کار کند: هیچ‌کاری.** بدون کلید هم LI.FI نرخ می‌دهد و مسیر اجرا
می‌شود. دو تنظیم اختیاری در انتهای سند هست: یکی سقف نرخ درخواست را بالا می‌برد،
یکی سهم کارمزد ما را روشن می‌کند. تا وقتی خاموش‌اند، **درآمد این تب صفر است ولی
کار می‌کند** — و اپ همین را صادقانه در `/api/health/cross-chain` می‌گوید.

## 🔴 چیزی که پیدا کردم و باید مستقیم بگویم

تب «میان‌زنجیره‌ای» نرخ واقعی نمی‌گرفت. این خط در `server/intentBridgeQuote.js` بود:

```js
estimatedOutput: amount || '999000',
fee: '1000',
estimatedTime: 120
```

یعنی هر کاربری که در Intent OS نرخ میان‌زنجیره‌ای می‌گرفت، **یک عدد ثابت
تایپ‌شده** می‌دید. نه از پل، نه از زنجیره، نه از هیچ‌جا. صفحهٔ Bridge نرخ واقعی
LI.FI را می‌گرفت، ولی آن یک مسیر جدا با کد جدا بود. پس دو سیستم داشتیم که یکی‌شان
دروغ می‌گفت و ظاهرشان از بیرون یکی بود.

سه چیز دیگر هم بود که با تست ۲۰۰ (OK) دیده نمی‌شد:

| مشکل | چرا خطرناک بود |
|---|---|
| صفحهٔ Bridge بعد از ارسال تراکنش مبدأ کارش تمام می‌شد | کاربر «ارسال شد» می‌دید و نمی‌فهمید پول هنوز به مقصد نرسیده |
| هیچ تاریخچه‌ای نوشته نمی‌شد | یک انتقال گیرکرده هیچ ردی در اپ نداشت |
| بخش HTLC اتمیک ظاهراً فعال بود | قرارداد مستقر نشده بود؛ دکمهٔ «اتمیک» روی هوا بود |

## حالا چه شکلی است — یک موتور، دو صفحه

```
 Intent OS ▸ تب «میان‌زنجیره‌ای»          صفحهٔ Bridge
 IntentCrossChainPanel.jsx               pages/Bridge.jsx
        │                                       │
        └──────────────┬────────────────────────┘
                       ▼
        src/services/cross-chain  ← تنها راه ورود
        ├─ core.js    نرمال‌سازی · رتبه‌بندی · ماشین وضعیت · اعتبارسنجی
        └─ client.js  انتقال HTTP + خط لولهٔ اجرا (موجودی → allowance →
                      شبکه → نرخ تازه → امضای کاربر → انتشار → رهگیری)
                       │
                       ▼  /api/cross-chain/*
        server/crossChain.js  ← موتور سمت سرور (همان core.js را import می‌کند)
        ├─ server/lifi.js          تنها کلاینت LI.FI؛ کلید و integrator اینجاست
        └─ server/crossChainStore.js  چهار مجموعهٔ داده + ماشین وضعیت
                       │
                       ▼
                  li.quest  →  زنجیره
```

نکتهٔ اصلی: `core.js` **هم در مرورگر و هم در سرور** اجرا می‌شود. یعنی عددی که
کارت نرخ نشان می‌دهد و عددی که سرور ثبت می‌کند از یک تابع می‌آیند و نمی‌توانند
با هم فرق کنند.

## API

همه با تگ `schema` و همه بدون کش (`no-store`) روی نرخ‌ها.

| مسیر | می‌دهد |
|---|---|
| `GET /api/cross-chain/chains` | فقط شبکه‌هایی که هم LI.FI دارد و هم کیف پول ما می‌تواند امضا کند |
| `GET /api/cross-chain/tokens?chain=&q=` | توکن‌های همان شبکه، قابل جست‌وجو |
| `GET /api/cross-chain/resolve-token` | نماد → قرارداد واقعی؛ نبود = ۴۰۴، نه توکن ساختگی |
| `GET /api/cross-chain/quote` | یک `CrossChainQuote` نرمال‌شده با انقضا |
| `GET /api/cross-chain/routes` | همهٔ مسیرها، امتیازدهی‌شده، به‌علاوهٔ `best` |
| `POST /api/cross-chain/transactions` | ثبت انتقال پس از داشتن هش واقعی مبدأ |
| `GET  …/transactions/:id/status` | وضعیت واقعی از LI.FI + ماشین وضعیت |
| `POST …/transactions/:id/cancel` | فقط پیش از انتشار؛ بعدش ۴۰۹ |
| `GET /api/cross-chain/history?wallet=` | تاریخچهٔ واقعی همان کیف پول |
| `GET /api/health/cross-chain?deep=1` | LI.FI · پل‌ها · integrator · دیتابیس · کیف پول · ایندکسر |

خطاها کد دارند، نه متن عمومی: `SAME_CHAIN` · `TOKEN_NOT_ON_CHAIN` ·
`EVM_ADDRESS_ON_SOLANA` · `AMOUNT_TOO_LOW` · `QUOTE_CHANGED` · `QUOTE_EXPIRED` ·
`INSUFFICIENT_BALANCE` · `USER_REJECTED` · `PROVIDER_RATE_LIMITED` … و هر کدام
یک جملهٔ فارسی در `crossChain.err.*` دارند.

## سه قاعده‌ای که کد را شکل داده

**۱. نرخ ساختگی ممنوع — حتی وقتی سرویس قطع است.**
اگر LI.FI جواب ندهد، کارت نرخ خالی می‌ماند و یک بنر می‌گوید سرویس مسیریابی در
دسترس نیست. هیچ عدد تخمینی جایش نمی‌نشیند. `/api/health/cross-chain` هم ۵۰۳
می‌دهد تا UI بداند نرخ نشان ندهد.

**۲. «کامل شد» فقط با هش تراکنش مقصد.**
LI.FI برای بعضی پل‌ها همان لحظه‌ای که پل انتقال را می‌پذیرد `DONE` می‌گوید.
`guardCompletion()` این را می‌گیرد و تا وقتی هش مقصد نیامده وضعیت را
`DESTINATION_PENDING` نگه می‌دارد، با این جملهٔ فارسی روی صفحه:

> «تراکنش مبدأ انجام شد. انتقال میان‌زنجیره‌ای هنوز در جریان است — این عملیات
> هنوز تمام نشده است.»

**۳. بهترین مسیر یعنی امتیاز، نه `routes[0]`.**
`scoreRoute()` = خروجی (با وزن روی حداقل دریافتی) − گس − کارمزدهای جداگانه −
هزینهٔ زمان − جریمهٔ بی‌اعتمادی. زمان ۰٫۲٪ به ازای هر ساعت حساب می‌شود؛ کوچک
است ولی به اندازه‌ای هست که مسیری که یک سنت بهتر و یک ساعت کندتر است ببازد.
هر مسیر `scoreBreakdown` دارد، پس رتبه‌بندی قابل بازبینی است.

## چه چیزی روشن است و چه چیزی صادقانه خاموش

| بخش | وضعیت | چرا |
|---|---|---|
| نرخ‌گیری و مقایسهٔ مسیر LI.FI | ✅ روشن | واقعی، بدون کش |
| اجرا از Intent OS و از Bridge | ✅ روشن | همان یک خط لوله |
| رهگیری مقصد + تاریخچه | ✅ روشن | از `/v1/status` |
| مقایسهٔ deBridge (DLN) در صفحهٔ Bridge | ✅ دست‌نخورده | قبلاً واقعی بود، رهایش کردم |
| تسویهٔ ترتیبی دوطرفه | ⚠️ زیر بخش «پیشرفته» | واقعی است ولی **اتمیک نیست** و برچسبش همین را می‌گوید |
| سواپ اتمیک HTLC | ⛔ خاموش | چک‌لیست شش‌بندی روی صفحه؛ تا هر شش‌تا سبز نشوند دکمه نمی‌آید |
| کارمزد ما روی بریج | ⛔ خاموش | `LIFI_FEE_READY` خالی است — fail-closed عمدی |
| دوام تاریخچه | ⚠️ مشروط | بدون `BLOB_READ_WRITE_TOKEN` تاریخچه در حافظه است و با ری‌استارت می‌رود؛ `/health` این را می‌گوید |

دربارهٔ HTLC: preimage همان‌طور که خواستی **از دستگاه بیرون نمی‌رود**. فقط در
`sessionStorage` می‌ماند، هرگز لاگ نمی‌شود، هرگز در بدنهٔ درخواست نمی‌رود؛ فقط
`keccak256` آن (hashlock) به سرور می‌رسد. تست این را جداگانه می‌سنجد.

## دو تنظیم اختیاری

```bash
# سقف نرخ درخواست LI.FI را بالا می‌برد. بدون آن هم کار می‌کند.
LIFI_API_KEY=

# سهم کارمزد ما (۰٫۳٪). تا 'true' نشود، درآمد صفر است — عمدی.
LIFI_FEE_READY=true
```

`/api/health/cross-chain` در بخش `integrator` دقیقاً می‌گوید ثبت شده‌ای یا نه؛
اگر نه، جمله‌اش این است: «bridging works, revenue is zero».

## یک تغییر جانبی که همین‌جا انجام شد

چت Intent OS جواب می‌داد:

```
Intent: PORTFOLIO. Prepared 1 real action(s).
```

این زبان داخلی برنامه‌ریز است، نه جواب آدم. حالا سرور یک `summary` ساختاریافته
می‌فرستد و کلاینت جمله را به زبان کاربر می‌سازد:

> «می‌توانم ۱۰۰ دلار USDC را روی Base تبدیل کنم. بررسی کن و تأیید کن — امضا با
> کیف پول توست و تا آن لحظه چیزی جابه‌جا نمی‌شود.»

و یک لایهٔ دوم (`scrubMachineTokens`) هر `actionId`، `routeId`، `tool_call` یا
نام enum را از هر متنی که از جای دیگری بیاید پاک می‌کند.
