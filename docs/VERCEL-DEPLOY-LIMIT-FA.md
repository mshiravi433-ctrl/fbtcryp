# چرا سایت به‌روز نمی‌شد — پیدا شد

> شما گفتید «برای ورسل ببین مشکل دوباره curl نیست، ببین مشکل کجاست».
>
> **درست حدس زدید که curl نیست.** مشکل را پیدا کردم و ربطی به کد نداشت.

> ⚠️ **به‌روزرسانی ۲۰۲۶-۰۹-۰۱ — سهمیه تنها علتِ «سایت به‌روز نمی‌شود» نیست.**
> همین علائم دوباره برگشت، و این‌بار سهمیه سالم بود (۱۱ دیپلوی در ۲۴ ساعت از
> سقف ۱۰۰). علت یک خط دیگر در **همین فایل** بود: یک `schedule` با فاصلهٔ کمتر
> از یک روز، که ورسل روی Hobby کل دیپلوی را رد می‌کند.
> تشخیص، قانون رسمی، و تستی که دیگر اجازه نمی‌دهد تکرار شود:
> **`docs/VERCEL-CRON-HOBBY-FA.md`**.
>
> و یک تمایز که کل تشخیص را کوتاه می‌کند: اگر روی commit **هیچ** وضعیت
> «Vercel» نیست → بیلدی ساخته نشده (سهمیه / اتصال git / `deploymentEnabled`).
> اگر وضعیت `failure | "Deployment failed."` هست → بیلد رد شده و علت در
> پیکربندی استقرار است، نه سهمیه.

## 🔁 تکرار ۲۰۲۶-۰۹-۲۹ — این بار خودِ رویداد push فایر نشد

> شما گفتید: «یک برنچ را مرج کردیم اما در ورسل نیامد و لایو نشد؛
> به نظرم دوباره curl مشکل خورده.»
>
> **باز هم curl نیست.** merge درست انجام شده و روی `main` نشسته؛ مشکل
> این‌جاست که گیت‌هاب **رویداد pushِ آن کامیت را به هیچ‌کس تحویل نداد** —
> نه به GitHub Actions، نه به ورسل.

### سه عدد که ماجرا را تمام می‌کند

PR #452 در `2026-09-29T08:29:29Z` مرج شد؛ کامیت squash شدهٔ آن
`e18d727ae62c0f06fe3145b283de3c2e2af32ff9` است (والدش `6f1ea12`).

| بررسی | کامیت قبلی `6f1ea12` (سالم) | کامیت جدید `e18d727` (مرج‌شده) |
|---|---|---|
| `actions/runs?head_sha=…` | **۱** ران (`Build APK`, event=`push`, ساخته‌شده `04:07:23Z`) | **۰** ران |
| `commits/<sha>/status` | **۱** وضعیت: `Vercel` → «Deployment has completed» | **۰** وضعیت (بیست دقیقه بعد از merge هم صفر بود) |
| آخرین رکورد `deployments` | `6f1ea12` ساعت `04:09:46Z` — یعنی ۲ دقیقه و ۲۶ ثانیه بعد از merge | هیچ رکوردی ساخته نشد |

`Build APK` با `on: [push, workflow_dispatch]` روی **هر** push بی‌قید و شرط
اجرا می‌شود. پس «ران ندارد» یعنی خودِ گیت‌هاب آن push را به صف نداده —
و ورسل که **بعد از** گیت‌هاب می‌شنود، طبیعتاً هیچ چیز برای شنیدن نداشته.

### چیزهایی که رد شدند (با عدد، نه با حدس)

- **سهمیهٔ دیپلوی:** در پنجرهٔ ۲۴ ساعتهٔ منتهی به `08:50Z` فقط **۹** دیپلوی
  ساخته شده (همه Production). سقف Hobby صد تاست. سهمیه علت نیست.
- **`vercel.json`:** آخرین بار `2026-09-26` با کامیت `f4a7083d84` عوض شده و
  در `6f1ea12` (که سالم دیپلوی شد) بایت‌به‌بایت همین فایل است. دست‌نخورده.
- **قانون cron روی Hobby:** هر سه `schedule` روزانه‌اند —
  `0 9 * * *`، `17 3 * * *`، `41 21 * * *`. رد.
- **`deploymentEnabled`:** فقط `arena/*` را خاموش می‌کند و `main` با آن
  مطابقت ندارد؛ همان تستِ «`main` هیچ‌وقت خاموش نشود» هم سر جایش است.
- **خودِ کد:** `npm run test:market-data` روی همین merge → **۶/۶ سبز**.

### سایت الان چه وضعی دارد

`GET https://fbtswap.ir/api/version` → `commit: 6f1ea12acb…`, `ref: main`,
`env: production`. یعنی پروداکشن هنوز **بیلد قبلی** است.

و دقیقاً همان خرابی که #452 برایش نوشته شده هنوز لایو است:

```
GET https://fbtswap.ir/api/markets?per_page=2
→ {"error":"UPSTREAM_FAILED","detail":"Upstream 403 for
   https://api.coingecko.com/api/v3/coins/markets?…per_page=2…"}
```

CoinGecko به سرور ۴۰۳ می‌دهد و بیلد فعلی هیچ فید زندهٔ جایگزینی ندارد —
همان چیزی که `server/providers.js` در #452 با failover به CoinLore حل کرد.

### درمان

چون رویداد push گم شده، **یک push تازه به `main`** رویداد را دوباره
شلیک می‌کند و ورسل HEAD را (که شامل #452 است) می‌سازد. این PR همان
push تازه است. اگر خواستید دستی انجامش دهید:

```bash
git checkout main && git pull
git commit --allow-empty -m "chore(deploy): re-fire the production push event"
git push origin main
```

⚠️ در داشبورد ورسل، **Redeploy** روی دیپلوی آخر این کار را نمی‌کند —
آن همان `6f1ea12` را دوباره می‌سازد، بدون فیکس. چیزی که لازم است یک
دیپلوی **جدید از HEAD** است.

### تستِ بعد از merge (دو دقیقه)

```bash
curl -s https://fbtswap.ir/api/version          # commitShort باید sha جدید باشد
curl -s 'https://fbtswap.ir/api/markets?per_page=2'   # باید سطر واقعی بدهد، نه UPSTREAM_FAILED
```

اگر بعد از merge **باز هم** روی کامیت هیچ وضعیت `Vercel` ننشست، آن‌وقت
اتصال گیتِ خودِ پروژه suspect است:
`vercel.com/dashboard` → پروژهٔ **`fbtcryp-kkxi`** → **Settings → Git**
(و همان‌جا چک کنید پروژهٔ دوم `fbtcryp4` حذف یا Disconnect شده باشد).

## خلاصهٔ یک خطی

**سهمیهٔ روزانهٔ دیپلوی ورسل تمام شده بود.** پلن رایگان ۱۰۰ دیپلوی در
هر ۲۴ ساعت می‌دهد؛ ما در ۲۴ ساعت گذشته **۱۱۱ تا** مصرف کرده بودیم.

هیچ خطایی هم نشان نمی‌دهد. فقط **بی‌صدا نمی‌سازد**. برای همین شبیه یک
معما به نظر می‌رسید نه یک خطا.

## چطور پیدایش کردم

اول فکر کردم باز هم `vercel.json` خراب شده — همان اشتباهی که قبلاً ۷
دیپلوی را کشت. **نبود.** فایل سالم بود، تست‌ها سبز، بیلد لوکال درست.

پس به‌جای حدس زدن، از API خودِ گیت‌هاب **شمردم**:

```
۴ مرداد   ۷۸ دیپلوی
۵ مرداد  ۱۲۸ دیپلوی   ← بیشتر از سقف
۲۴ ساعت گذشته: ۱۱۱ دیپلوی
```

سقف پلن رایگان ورسل **۱۰۰ تا در هر ۸۶۴۰۰ ثانیه** است. رد شدیم.

## بودجه کجا رفت — نکتهٔ اصلی

این بخش مهم است. **هر یک push، چهار دیپلوی می‌ساخت.**

**دو پروژهٔ ورسل** به این مخزن وصل‌اند، و هر کدام برای **همان یک کامیت**
هم Production می‌سازد هم Preview:

```
Production – fbtcryp-kkxi   ← این یکی سایت واقعی است
Preview    – fbtcryp-kkxi
Production – fbtcryp4       ← این چیست؟ کسی نگاهش نمی‌کند
Preview    – fbtcryp4
```

برای هر کامیت جداگانه شمردم و الگو کاملاً واضح است:

| کامیت | تعداد دیپلوی |
|---|---|
| `437ed89d` | ۴ |
| `6246ce30` | ۴ |
| `547be9cc` | ۳ ← سهمیه دارد تمام می‌شود |
| `c928d69b` | **۱** |
| `492efa9d` | ۳ |
| `ac499730` | **۰** ← اصلاً ساخته نشد |

**فقط `fbtcryp-kkxi` روی `fbtswap.ir` می‌نشیند.** یعنی **سه‌چهارم** بودجه
صرف بیلدهایی می‌شد که هیچ‌کس نمی‌بیند.

## چه کاری کردم (رایگان)

در `vercel.json` این را اضافه کردم:

```json
"git": {
  "deploymentEnabled": {
    "arena/*": false
  }
}
```

**یعنی:** برای شاخهٔ کاری، دیگر Preview نساز.

**Production دست‌نخورده می‌ماند**، چون Production شاخهٔ `main` را دنبال
می‌کند و `main` با الگوی `arena/*` مطابقت ندارد.

⚠️ این خطرناک‌ترین بخش تغییر بود و برایش تست گذاشتم: اگر الگویی بنویسم
که `main` را هم بگیرد، **Production کاملاً خاموش می‌شود** و علامتش
دقیقاً همین باگی است که می‌خواهم درستش کنم — سایت بی‌صدا به‌روز نشدن.
تست جدید مطمئن می‌شود `main` هیچ‌وقت خاموش نشود.

**نتیجه: مصرف نصف می‌شود، بدون یک ریال هزینه.**

و `git` یک کلید **رسمی** ورسل است — قبل از اضافه کردن، مستنداتش را چک
کردم. این همان جایی است که قبلاً با کلید `"//"` هفت بیلد را سوزاندم، پس
این بار حدس نزدم.

## 🔴 کاری که فقط از دست شما برمی‌آید

نصف دیگر مشکل، **پروژهٔ دوم** است و از داخل کد قابل حل نیست.

### آن پروژهٔ `fbtcryp4` را حذف کنید

۱. 🔗 **https://vercel.com/dashboard**
۲. پروژهٔ **`fbtcryp4`** را پیدا کنید (نه `fbtcryp-kkxi`)
۳. بازش کنید → **Settings**
۴. پایین بروید تا **Delete Project**

**اگر می‌ترسید حذفش کنید** (که ترس منطقی‌ای است)، به‌جای حذف فقط اتصال
گیت را قطع کنید:

۱. `fbtcryp4` → **Settings** → **Git**
۲. **Disconnect** را بزنید

با این کار پروژه می‌ماند ولی دیگر با هر push بیلد نمی‌شود.

### چطور مطمئن شوید کدام درست است

قبل از حذف، مطمئن شوید `fbtcryp4` دامنهٔ `fbtswap.ir` را ندارد:

- `fbtcryp4` → **Settings** → **Domains**
- اگر آنجا `fbtswap.ir` نبود → حذفش امن است
- اگر بود → **حذف نکنید** و به من بگویید

## کِی سایت دوباره به‌روز می‌شود؟

سقف **پنجرهٔ ۲۴ ساعتِ کشویی** است، نه ساعت ۱۲ شب. یعنی هر دیپلوی
دقیقاً ۲۴ ساعت بعد از خودش آزاد می‌شود.

قدیمی‌ترین دیپلوی‌های داخل پنجره مربوط به **۵ مرداد ساعت ۰۳:۱۵ UTC**
هستند. پس از حدود همان ساعت فردا، ظرفیت کم‌کم آزاد می‌شود و اولین push
بعدی ساخته می‌شود.

**کاری لازم نیست بکنید — خودش می‌آید.** فقط اگر عجله دارید، `fbtcryp4`
را حذف کنید تا ظرفیت زودتر آزاد شود.

## چیزی که یاد گرفتم

وقتی سایت به‌روز نمی‌شد، **دو بار** حدس زدم که «صف بیلد ورسل کند است»
و به شما هم همین را گفتم. آن حدس بود، نه تشخیص.

جوابش با **شمردن** پیدا شد، نه با حدس زدن: تعداد دیپلوی در روز، تعداد
دیپلوی به ازای هر کامیت، و تعداد در پنجرهٔ ۲۴ ساعته. سه تا عدد ساده که
از همان اول در دسترس بودند.

**درسش:** وقتی چیزی «کند» به نظر می‌رسد، اول بشمار. «کند است» یک تشخیص
نیست.
