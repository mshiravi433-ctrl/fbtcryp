# بازبینی امنیتی FlashLiquidityRouter — فاز ۱۵۲ (خودبازبینی + شواهد تمرین)

> **این سند ممیزی مستقل نیست و ادعایش را هم ندارد.** فلگ
> `FLASH_LIQUIDITY_ROUTER_AUDITED` تا انتشار گزارش یک ممیز بی‌طرف `false` می‌ماند.
> چیزی که اینجا می‌خوانید: خودبازبینی خط‌به‌خط، شواهد اجرای واقعی روی EVM محلی،
> و لیست دقیق مواردی که ممیز مستقل باید روی آن‌ها تمرکز کند.

## ۱) یافتهٔ واقعی تمرین — باگ reparment در مسیر Balancer (پیدا و اصلاح شد)

تمرین سطح ۲ (`npm run rehearse:flash-liquidity`) در اولین اجرا با خطای
`BALANCE_NOT_REPAID` شکست خورد — و این **مهم‌ترین خروجی کل تمرین** بود:

- **باگ:** `receiveFlashLoan` بازپرداخت را فقط با `approve` تأیید می‌کرد.
- **واقعیت پروتکل:** Vault بالانتر پول را **نمی‌کشد**؛ گیرنده باید خودش
  `amount + fee` را برگرداند و Vault فقط موجودی‌اش را چک می‌کند و در کمبود، کل
  تراکنش را revert می‌کند.
- **نتیجهٔ باگ روی mainnet:** هر فلش لان بالانتر با خطای کمبود بازپرداخت شکست
  می‌خورد (گاز سوخته، نه ضرر اصل) — و شاید خطرناک‌تر: حالت ذهنی «approve کافی است».
- **اصلاح:** انتقال فعال `amount + fee` برای هر توکن قبل از sweep سود.
  تمرین بعدی: ۱۶/۱۶ پاس.

## ۲) سطح تمرین (شواهد)

`test/flash-liquidity/rehearsal-report.json` — چرخهٔ کامل روی EVM محلی:

- دیپلوی قرارداد واقعی از همان آرتیفکت باندل‌شده + allowlist؛
- اختلاف قیمت واقعی بین دو استخر constant-product؛
- پلنر روی reserveهای واقعی زنجیره: وام بهینه ۱۴,۸۷۲.۴۷ USDC، مسیر pair-2→pair-1؛
- شبیه‌سازی واقعی `eth_call` قبل از امضا → `EXECUTE_READY`؛
- اجرای امضاشده: وام → دو hop → بازپرداخت کامل (موجودی Vault دست‌نخورده) →
  سود ۱۷۶.۱۶ USDC به `profitTo` → قرارداد صفرِ صفر شد (بدون dust)؛
- **مسیر ناموفق:** نسخهٔ طماع با `minProfit` غیرواقعی → گیت شبیه‌سازی رد کرد
  (هیچ‌چیز امضا/ارسال نشد)؛ ارسال اجباری → revert اتمیک، موجودی‌ها دست‌نخورده.

**محدودهٔ صداقت:** توکن‌ها MockERC20، Vault هارنسِ با همان سمانتیک بالانتر،
استخرها MiniPair با فرمول دقیقاً برابر پلنر. زنجیره، EVM محلی است — فورک
mainnet نیست (سندباکس دسترسی به RPC بلاکچین ندارد). Aave/Balancer زنده، گاز
واقعی و MEV واقعی از شواهد این تمرین خارج‌اند.

## ۳) خودبازبینی خط‌به‌خط (چک‌لیست)

| مورد | وضعیت |
|---|---|
| callback فقط از source فعال در همان تراکنش (`_activeSource`) | ✓ |
| `initiator == address(this)` در مسیر Aave | ✓ |
| `PRE_EXISTING_BALANCE` قبل از هر وام — حسابداری دقیق | ✓ |
| چک on-chain `INSUFFICIENT_PROFIT` — زیان‌ده تسویه نمی‌شود | ✓ (تمرین: تأیید دوجهته) |
| allowlist سه‌گانه: source / asset / target — فقط owner | ✓ |
| executor فقط «شروع» می‌کند؛ allowlist/جابه‌جایی سود/مالکیت قفل است | ✓ |
| dust توکن میانی → abort کامل | ✓ (تمرین: صفرِ صفر) |
| `nonReentrant` روی مسیرهای ورودی و rescue | ✓ |
| `rescue` فقط owner — برای توکن‌های اهدایی اشتباهی | ✓ |
| `receive()` → revert — قرارداد ETH نمی‌پذیرد | ✓ |
| deadline در هر سه لایه (planner/params/callback) | ✓ |
| سقف `MAX_HOPS = 6` | ✓ |
| bubble شدن revert data تارگت برای دیباگ | ✓ |
| بازپرداخت فعال در مسیر Balancer | ✓ (اصلاح شد — بند ۱) |

## ۴) برای ممیز مستقل — کجاها را دقیق‌تر نگاه کنید

1. **فرض توکن غیراستاندارد:** USDT-مانند (بدون bool) در `transferFrom` داخل
   استخرها/DEXهای واقعی؛ `safeApprove` دوجهته (0 → max → 0) و مسیر `ret.length==0`.
2. **تیک‌بازگشتی از طریق target مجاز:** targetهای allowlist قابل اعتماد فرض
   شده‌اند — هر targetی که owner اضافه می‌کند عملاً در trust base است (سند بدهید).
3. ** rebalancing سود چند-توکنی:** مسیر Balancer چند-دارایی فقط `tokens[0]` را
   settlement می‌داند؛ ممیزی سناریوی چند-توکنی را تأیید کند.
4. **مرتب‌سازی hop و dust:** فرض «خروجی دقیق hop قبلی = ورودی hop بعدی» به
   calldata ساخته‌شدهٔ خارج از قرارداد وابسته است؛ اگر اختلاف کرد → `HOP_OUTPUT_TOO_LOW`
   یا `DUST_LEFT_ON_INTERMEDIATE` — ممیزی مسیرهای خطا را تأیید کند.
5. **Aave premium متغیر:** `premium` از event/callback می‌آید نه از عدد ثابت —
   سناریوی تغییر premium بین quote و اجرا باید revert بدهد نه ضرر.
6. ** گس بازگشت از revert:** دنایمیک بودن گازِ revert در صف/باندل — در سطح
   ارسال خصوصی مدیریت می‌شود، نه قرارداد.
