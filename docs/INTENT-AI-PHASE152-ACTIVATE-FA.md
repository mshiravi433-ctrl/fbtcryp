# فعال‌سازی فلش لیکوییدیتی (فاز ۱۵۲) — گام به گام

> قانون ثابت اول: **تا ممیزی مستقل انجام نشود، اجرای واقعی باز نمی‌شود.**
> این محدودیت باگ نیست؛ همان صداقتی است که بقیهٔ Intent OS را معتبر نگه می‌دارد.
> در هر سطح از این راهنما، دقیقاً می‌گوییم چه چیزی روشن می‌شود و چه چیزی هنوز بسته می‌ماند.

سه سطح فعال‌سازی داریم:

| سطح | چه چیزی روشن می‌شود | چه چیزی هنوز بسته است |
|---|---|---|
| ۰ — پلنر و آموزش | صفحهٔ `/#/flash-liquidity`، خط لولهٔ ۹ مرحله‌ای، API خشک scan/plan | اجرای واقعی |
| ۱ — اتصال قرارداد | وضعیت استقرار در capabilities؛ قرارداد آماده روی زنجیره | اجرای واقعی (planning-only می‌ماند) |
| ۲ — اجرای واقعی | امضای تراکنش فلش لان از کیف پول | — (نیازمند ممیزی + شبیه‌سازی) |

---

## سطح ۰ — همین حالا فعال است (هیچ کاری لازم نیست)

این‌ها با همان کامیت فاز ۱۵۲ کار می‌کنند:

1. **صفحهٔ آموزشی:** `https://<دامنه‌ات>/#/flash-liquidity`
   - اینتنت فارسی می‌گیرد (همان «با ۰ سرمایه اولیه…»)، خط لولهٔ ۹ مرحله‌ای را
     کامل نشان می‌دهد، جدول سود/گاز/کارمزد می‌سازد و اگر سود کافی نباشد
     صادقانه می‌گوید «معامله‌ای ارسال نشد».
2. **API خشک:** هیچ کلیدی نمی‌خواهد.

چک سریع از ترمینال:

```bash
curl -s https://<دامنه‌ات>/api/flash-liquidity/v1/capabilities | python3 -m json.tool | head
```

انتظار: `"status": "planning-only"` و لیست `missing`.

روی وب‌سایت رسمی، این قابلیت بعد از merge این برنچ به `main` و دیپلوی خودکار
Vercel برای همهٔ کاربران فعال می‌شود. برای ساخت APK هم مسیر همان
`build-apk.yml` همیشگی است.

## سطح ۱ — اتصال قرارداد روی یک زنجیره

نتیجه: قرارداد واقعی روی زنجیره دیپلوی و allowlist می‌شود و سرور وضعیتش را
نشان می‌دهد. **اجرا همچنان planning-only می‌ماند** (و باید هم بماند).

### گام ۱ — کامپایل

```bash
npm ci
npm run compile:flash-liquidity
```

انتظار: `✓ compiled FlashLiquidityRouter` و حجم زیر ۲۴KB.

### گام ۲ — کیف پول دیپلوی‌کننده

- یک **کیف پول دورریز** بساز (فقط کمی گاز داشته باشد؛ هرگز کلید اصلی‌ات نباشد).
- کلید را فقط در env بده؛ در هیچ فایلی ذخیره نکن.

### گام ۳ — آدرس‌های زنجیره را جمع کن

برای هر زنجیره سه چیز لازم است:

| چه چیزی | از کجا | وضعیت در رجیستری |
|---|---|---|
| منبع فلش لان | Balancer Vault یکسان روی همهٔ زنجیره‌های V2 — از [docs.balancer.fi](https://docs.balancer.fi/concepts/vault/flashloans.html) | ✓ همین حالا verified (۸ زنجیره)؛ Aave فقط اتریوم |
| توکن تسویه (مثلاً USDC) | آدرس رسمی توکن روی همان زنجیره | باید در `FLASH_ASSETS` بدهی |
| تارگت DEX (router استخرهای V2 یا aggregator) | آدرس رسمی همان DEX | باید در `FLASH_TARGETS` بدهی |

> آدرس‌ها را **فقط** از مستندات رسمی پروتکل بردار. آدرس اشتباه = گاز سوخته یا
> بدتر. اگر زنجیره‌ای در رجیستری (`FLASH_PROVIDER_REGISTRY` در
> `src/lib/intent-ai/flashLiquidity.js`) نیست، اول آنجا اضافه‌اش کن.

### گام ۴ — دیپلوی + allowlist در یک فرمان

```bash
DEPLOYER_PRIVATE_KEY=0x... \
RPC_URL=https://<rpc-همان-زنجیره> \
CHAIN_ID=42161 \
FLASH_ASSETS=0xaf88d065e77c8cC2239327C5EDb3A432268e5831 \
FLASH_TARGETS=0x<router-dex-1>,0x<router-dex-2> \
node scripts/deploy-flash-liquidity.mjs
```

اسکریپت خودش:

- منبع فلش را از رجیستری verified برمی‌دارد (Balancer Vault)؛
- قرارداد را دیپلوی می‌کند؛
- `setFlashSource` / `setAsset` / `setTarget` را همان‌جا تنظیم می‌کند؛
- در انتها **خط دقیق env** را چاپ می‌کند که باید paste کنی.

اگر `FLASH_TARGETS` ندهی، قرارداد **خنثی و امن** دیپلوی می‌شود (هر hop با
`TARGET_NOT_ALLOWED` رد می‌شود) — بعداً با `setTarget` اضافه کن.

### گام ۵ — env سرور را بگذار

خروجی گام ۴ (مثال):

```bash
FLASH_LIQUIDITY_ROUTER_ADDRESSES=42161:0xYourRouter
```

در Vercel (یا سرور API) بگذار و redeploy کن. بعد چک کن:

```bash
curl -s https://<دامنه‌ات>/api/flash-liquidity/v1/capabilities | python3 -m json.tool | grep -E "status|missing"
```

`ROUTER_CONTRACT_NOT_CONFIGURED` از لیست `missing` حذف شده — دو گیت دیگر
(ممیزی، شبیه‌سازی) هنوز عمداً باز نشده‌اند.

### گام ۶ — مالکیت را منتقل کن

کیف پول دورریز دیگر لازم نیست. با هاردوالت (یا multisig):

```
transferOwnership(<آدرس-هاردوالت>)
```

## سطح ۲ — اجرای واقعی (فقط بعد از این سه گیت)

### گیت الف — ممیزی مستقل

- قرارداد را به یک ممیز مستقل بده (گزارش واقعی، نه خوداظهاری).
- **فقط بعد از** انتشار گزارش:

```bash
FLASH_LIQUIDITY_ROUTER_AUDITED=true
```

> این فلگ یعنی «گزارش ممیزی موجود است»، نه «انشاء کنید». دروغ گفتن به این
> فلگ یعنی دور زدن تنها حفاظ کاربر.

### گیت ب — شبیه‌سازی (مرحلهٔ ۷ خط لوله)

هیچ تراکنشی نباید بدون شبیه‌سازی موفق امضا شود. سه راه عملی:

1. مسیر موجود پروژه: pre-sign simulation سواپ (`src/lib/preSignSimulation.js`)
   به گیت وصل می‌شود؛
2. `eth_call` روی `executeArbitrage*` با state تازهٔ بلاک؛
3. Tenderly/similar برای شبیه‌سازی bundle.

تا این اتصال انجام نشود، `SIMULATION_UNAVAILABLE` در `missing` می‌ماند —
و باید بماند.

### گیت ج — تمرین روی فورک محلی (پیشنهاد جدی)

Aave/Balancer روی اکثر تست‌نت‌ها مستقر نیستند، پس تمرینِ درست = فورک mainnet:

```bash
anvil --fork-url https://<rpc-arbitrum>
# http روی loopback مجاز است:
DEPLOYER_PRIVATE_KEY=0x... RPC_URL=http://127.0.0.1:8545 CHAIN_ID=42161 \
  FLASH_ASSETS=0xaf88d065e77c8cC2239327C5EDb3A432268e5831 \
  FLASH_TARGETS=0x<router> \
  node scripts/deploy-flash-liquidity.mjs
```

روی فورک: یک فرصت آربیتراژ مصنوعی بساز (قیمت یک استخر را دستکاری کن)،
اسنپ‌شات‌ها را از همان فورک بخوان، و کل چرخهٔ plan → simulation → امضا →
بازپرداخت را ببین که یا سود می‌سازد یا کل تراکنش revert می‌شود.

### اجرای اول واقعی

- فقط با امضای دستی کیف پول (نه ربات)؛
- مبلغ آزمایشی کوچک؛
- فقط ارسال خصوصی (private relay/bundle) — ممپول عمومی همیشه رد است؛
- اتاقک تلاش روزانهٔ policy (`dailyMaxAttempts`) را کم نگه دار.

## جمع‌بندی وضعیت‌ها

| وضعیت `capabilities` | معنی |
|---|---|
| `planning-only` + `missing` | طبق معمول؛ پلنر فعال، اجرا بسته |
| `execution-gated-by-wallet` | هر سه گیت سبز؛ فقط امضای کاربر کم است |

قانون نهایی: اگر در `missing` چیزی ماند، آن چیزی که مانده **سند است، نه مانع**.
