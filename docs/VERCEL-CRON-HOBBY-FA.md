# سایت به‌روز نمی‌شود — این بار علت: یک خط `crons` در `vercel.json`

> تاریخ تشخیص: ۲۰۲۶-۰۸-۳۱ (سه‌شنبه) — ۲۳:۴۱ UTC
> گزارش کاربر: «تغییرات در ورسل دیپلوی نمیشه و لایو نمیشه در سایت»
> وضعیت: **در کد اصلاح شد** (این فایل + تست + یک خط در `vercel.json`)

---

## خلاصهٔ یک‌خطی

یک cron با برنامهٔ **هر ۱۰ دقیقه** به `vercel.json` اضافه شد.
پلن رایگان (Hobby) ورسل cron را فقط **روزی یک‌بار** می‌پذیرد؛ اگر عبارت
کرون بیشتر از روزی یک بار بزند، ورسل **کل دیپلوی را رد می‌کند** — نه فقط
همان cron را. یعنی از آن لحظه **هیچ** push به `main` بیلد نشد و سایت روی
همان بیلد قبلی ماند.

سه خط پایینِ همین فایل کل ماجراست:

```diff
   "crons": [
     { "path": "/api/cron/daily",      "schedule": "0 9 * * *"  },
     { "path": "/api/cron/train",      "schedule": "17 3 * * *" },
+    { "path": "/api/cron/smart-money", "schedule": "*/10 * * * *" }   ← قاتل
   ]
```

## نشانه‌ها — چطور تشخیص داده شد

اولین حدس «باز هم سهمیهٔ ۱۰۰ دیپلوی» بود (`docs/VERCEL-DEPLOY-LIMIT-FA.md`).
**نبود.** این‌بار شمارش فرق داشت:

| روز | دیپلوی‌های ثبت‌شده در گیت‌هاب |
|---|---|
| ۲۹ مرداد | ۴ |
| ۳۰ مرداد | ۱۱ |
| ۳۱ مرداد | ۱۱ |

سهمیه اصلاً پر نشده بود. پس سراغ خودِ وضعیت‌های commit رفتم — و این‌بار
ورسل ** حرف می‌زد **:

```
573d85a4  23:41  Vercel => failure | "Deployment failed."
66e5d4f2  22:16  Vercel => failure | "Deployment failed."
e275cab0  21:51  Vercel => failure | "Deployment failed."
62549a4c  21:45  Vercel => success | "Deployment has completed"   ← آخرین بیلد زنده
```

دستور دقیق، برای دفعهٔ بعد:

```bash
gh api "repos/OWNER/REPO/commits/$(git rev-parse HEAD)/status" \
  --jq '.statuses[] | .context + " => " + .state + " | " + .description'
```

**«failure روی commit» یعنی پلتفرم بیلد را دیده و رد کرده؛
«هیچ وضعیتی روی commit» یعنی اصلاً بیلدی نساخته** (سهمیه، اتصال git،
یا `deploymentEnabled`). این دو حالت دو بیماری متفاوت‌اند و درمانشان هم
متفاوت است.

بعد مقایسه کردم آخرین کامیت موفق را با HEAD:

```bash
gh api "repos/OWNER/REPO/compare/<sha-موفق>...<sha-الان>" --jq '.files[] | .status + " " + .filename'
```

از ۳۲ فایل تغییریافته، **دو** فایل روی مسیر بیلد اثر داشتند:
`package-lock.json` (بازگردانی شده به حالت سالم) و `vercel.json`.
همین. همان یکی که هیچ‌وقت در رادار نبود.

برای قطع شک، بیلد را دقیقاً همان‌طور که ورسل اجرا می‌کند لوکال زدم:

```
npm ci && npm run build:full
  ✓ built in 26.51s
  ▸ generated 7 landing pages + sitemap
```

سبز. یعنی کد سالم است — مشکل از **پیکربندی استقرار** است، نه از بیلد.

## قانون واقعی ورسل (و افسانه‌ای که در مخزن جا افتاده بود)

مستندات رسمی، بخش Usage & Pricing برای Cron Jobs:

> Hobby accounts are limited to cron jobs that run once per day. Cron
> expressions that would run more frequently will fail during deployment.
> _«Hobby accounts are limited to daily cron jobs. This cron expression would
> run more than once per day.»_

و جدول محدودیت‌ها:

| پلن | تعداد cron در هر پروژه | کمترین فاصلهٔ اجرا |
|---|---|---|
| **Hobby** | **۱۰۰** | **روزی یک‌بار** |
| Pro | ۱۰۰ | دقیقه‌ای |

نکتهٔ مهم که در این مخزن **غلط** نوشته شده بود: هم در `server/app.js` و هم
در تست `test/wiring.mjs` ادعا شده بود «Hobby فقط ۲ تا cron مجاز است».
این عدد از دوران بتای کرون‌های ورسل (۲۰۲۱) مانده بود. دقیقاً همین عددِ
کهنه باعث شد کسی که cron سوم را اضافه کرد فکر کند مشکل «تعداد» است و
دنبال تعداد برود، در حالی که مشکل **فاصلهٔ زمانی** بود.

در نتیجه: عدد ۲ به «سقف بودجهٔ خودمان = ۳» تبدیل شد (تصمیم خودمان، نه
محدودیت پلتفرم) و قانون اصلی — روزی‌یک‌بار — همان‌جا تست شد. اگر روزی خواستید
cron چهارم اضافه کنید، اول یکی را حذف کنید؛ دلیلش هزینهٔ اجراست، نه ورسل.

### چرا این باگ گران تمام شد

1. `vite build` هرگز `vercel.json` را نمی‌خواند. بیلد لوکال سبز است.
2. `crons` آرایه‌ای از رشته‌هاست؛ هیچ اسکیمای پایداری آن را در CI کنترل نمی‌کند.
3. خطا در «ساخت دیپلوی» می‌افتد، پس در لاگ بیلد چیزی نیست که بشود خواند.
4. نشانهٔ ظاهری‌اش با «سایت کند است»، «CDN کشیده»، «سهمیه تمام شده» و
   «اتصال git خراب» یکی است. چهار تشخیص رفت و هر چهار تا غلط بود.

## کاری که کردم

### ۱) `vercel.json` — برنامه به روزی یک‌بار تغییر کرد

```json
{ "path": "/api/cron/smart-money", "schedule": "41 21 * * *" }
```

**۲۱:۴۱ UTC**، دقیقاً ۱۲ ساعت بعد از `daily` (۰۹:۰۰). عمداً نه هم‌ساعت با
`train` (۰۳:۱۷) و نه هم‌ساعت با `daily`: اگر دو cron هم‌زمان بیفتند، یکی‌شان
روی همان Function سرد می‌نشیند و ممکن است به `maxDuration` برسد.

### ۲) هیچ قابلیتی حذف نشد

مهم‌ترین نکته: لازم نبود `/api/cron/smart-money` حذف شود یا route‌اش ببندد.
اسلات روزانهٔ `daily` **از قبل** همان چرخه را اجرا می‌کند:

```js
smartMoney.runAlertCycle(async (endpoint, _lang, payload) =>
  deliverStagePush(endpoint, { ... }))
```

پس «هر ۱۰ دقیقه» عملاً چیزی اضافه نمی‌کرد که «روزی دو بار» ندارد — و
`runAlertCycle` با کلید `watch + event + type` و cooldown هر watch،
dedupe می‌شود؛ دو اجرا در روز یعنی پنجرهٔ شکار بزرگ‌تر، نه دو نوتیفیکیشن
تکراری برای یک کاربر.

### ۳) تست‌های جدید در `test/wiring.mjs`

- هر cron در `vercel.json` باید حداکثر روزی یک بار بزند (تجزیهٔ واقعی فیلد
  دقیقه/ساعت، شامل `*/n`، لیست و بازه).
- سقف سه cron — بودجهٔ خودمان، با توضیح اینکه چرا.
- هیچ دو cron روی یک اسلات ننشینند.
- مسیر هر cron واقعاً در `server/app.js` وجود داشته باشد (وگرنه روزی یک‌بار
  ۴۰۴ تا ابد).
- اگر کسی وسوسه شد cron را حذف کند، چرخهٔ هشدار در `daily` بماند — تا
  «اصلاح پیکربندی» تبدیل به «حذف بی‌صدای یک قابلیت» نشود.
- و اینکه `main` هیچ‌وقت با `deploymentEnabled` خاموش نشود (تست قبلی).

## کاری که فقط از دست شما برمی‌آید

### ۱) PR را merge کنید

شاخهٔ کاری `arena/*` عمداً روی ورسل **دیپلوی نمی‌شود** (تعمیرِ همان مشکل
سهمیه — `docs/VERCEL-DEPLOY-LIMIT-FA.md`). پس تا وقتی تغییر merge نشود،
سایت به‌روز **نمی‌شود** و این باگ نیست، تنظیم خودمان است:

> «تغییرات در ورسل دیپلوی نمیشه» = دو علت جدا دارد:
> ۱) تغییر روی `arena/*` است → ورسل بی‌صدا رد می‌کند.
> ۲) تغییر روی `main` است ولی بیلد رد می‌شود ← **موضوع همین فایل**.

### ۲) بعد از merge، یک‌بار وضعیت را ببینید

```bash
gh api "repos/mshiravi433-ctrl/fbtcryp/commits/main/status" \
  --jq '.statuses[] | .state + " | " + .description'
```

انتظار: `success | Deployment has completed`. اگر `failure` بود،
`target_url` را باز کنید — این‌بار لاگ هست.

### ۳) دامنهٔ لاو را با یک نشانهٔ نسخه چک کنید

`fbtswap.ir` یک کش `max-age=0, must-revalidate` روی `index.html` دارد، پس
لازم نیست cache-buster بزنید؛ ولی Service Worker نسخهٔ قبلی را نگه می‌دارد.
اگر سایت آپدیت شد ولی شما تغییر را ندیدید: DevTools → Application →
Service Workers → **Unregister**، یا حالت Incognito.

## چک‌لیست — قبل از اینکه به `vercel.json` دست بزنید

1. `vercel.json` **کامنت نمی‌پذیرد**. یک کلید `//` برای کامنت گذاشتن، کل
   فایل را نامعتبر کرد و هفت بیلد را سوزاند. (بخش ۱۲ تست همین را نگه می‌دارد.)
2. هر کلیدی که اضافه می‌کنید باید در اسکیمای رسمی باشد:
   `https://openapi.vercel.sh/vercel.json` — ورسل `additionalProperties: false`
   دارد، یعنی کلید اختراعی هشدار نمی‌دهد، بیلد را می‌کشد.
3. هر `schedule` باید **روزی یک‌بار** باشد. همین.
4. هر `path` باید یک route واقعی زیر `/api/` باشد و با `CRON_SECRET` محافظت
   شود (وگرنه هر کسی می‌تواند کرون را دستی بزند).
5. بعد از تغییر، تست را اجرا کنید — این خط دقیقاً برای همین نوشته شد:

   ```bash
   node test/run.mjs 2>&1 | grep -iE "cron|vercel"
   ```

6. تغییر را merge کنید تا روی سایت بنشیند؛ `arena/*` دیپلوی نمی‌شود.

## سه درس عمومی

- **محدودیت‌های پلتفرم را از مستندات روز بخوانید، نه از کامنت‌های مخزن.**
  عدد «۲ تا cron» دو بار ما را گمراه کرد: یک بار در `server/app.js`، یک بار
  در تست. کامنتِ کهنه از تستِ کهنه بدتر است، چون تست به اشتباه سبز است.
- **فایل‌های پیکربندی بی‌آزمون، خطرناک‌ترین کد یک پروژه‌اند.** `vite build`
  و `npm test` هیچ‌کدام `vercel.json` را نمی‌خواندند؛ تا امروز که می‌خوانند.
- **نشانهٔ «هیچ اتفاقی نیفتاد» با نشانهٔ «اتفاق افتاد و رد شد» فرق دارد.**
  کل تشخیص این پرونده در یک ستون `gh api .../status` جا می‌شد؛ اگر بار اول
  همان را دیده بودیم، دو ساعت و سه حدسِ غلط صرفه‌جویی می‌شد.
