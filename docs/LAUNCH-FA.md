# FBT لانچ — Launchpad توکن و نقدینگی

**ماژودال، غیرامانی، و مستقل — بدون حذف یا تغییر هیچ صفحه‌ای از FBT سواپ.**

FBT لانچ یک ماژول اضافه‌شده (additive) است که کاربر می‌تواند:
توکن بسازد → روی شبکهٔ دلخواه دیپلوی کند → استخر نقدینگی بسازد →
نقدینگی اولیه را با قیمت اولیهٔ انتخابی اضافه کند → راه‌اندازی را شروع کند →
قرارداد را روی زنجیره تأیید کند → صفحهٔ توکن را داشته باشد → توکن قابل
سواپ شود.

---

## ۱. قانون غیرامانی (غیرقابل تغییر)

- **FBT هرگز دارایی کاربر را نگهداری نمی‌کند.**
- **FBT هرگز کلید خصوصی یا Seed Phrase کاربر را نمی‌گیرد.**
- **FBT هرگز به‌جای کاربر تراکنش مالی امضا نمی‌کند.**

در عمل:
- API فقط **بایت‌های آماده** (calldata) تولید می‌کند — `prepareTransaction()`.
- هر امضا در **کیف‌پول خود کاربر** انجام می‌شود (MetaMask، WalletConnect، …).
- بک‌اند فقط هش‌های عمومی تراکنش را می‌بیند.
- توکن‌ها مستقیم به آدرس سازنده می‌زنند؛ توکن‌های LP هم مستقیم به کیف‌پول
  سازنده — بدون قرارداد قفل، بدون واسطه، بدون نهادی که «نباید اعتماد کرد ولی
  باید کرد».

این قانون در چهار لایه اجرا شده است:
1. **معماری:** API stateless است و کلید ندارد.
2. **منطق:** موتور state machine فقط با `signer` کاربر پیش می‌رود.
3. **داده:** تاریخچهٔ محلی و رکورد عمومی فقط فیلدهای غیرحساس را نگه می‌دارند
   (لیست بستهٔ `ALLOWED_FIELDS`؛ هر فیلد دیگر در مرز حذف می‌شود).
4. **دسترس‌پذیری:** صفحهٔ /launch و خروجی `/api/launch/config` این بیانیه را
   همیشه به کاربر نشان می‌دهند.

## ۲. شبکه‌ها (فاز ۱: EVM)

| شبکه | DEX | توضیح |
|------|-----|-------|
| Base | Uniswap V2 (fork) | — |
| BNB Chain | PancakeSwap V2 | — |
| Arbitrum | SushiSwap V2 | — |
| Polygon | QuickSwap V2 | — |
| Ethereum | Uniswap V2 | — |

**چرا V2 و نه Uniswap v4؟** v4 روی BNB وجود ندارد و جریان initialisation
آن (hook-aware) فرایند متفاوتی دارد. فاز ۱ روی استخرهایی می‌آید که **همین
الان** در FBT سواپ هم مسیریابی می‌شوند: ساخته می‌شوند، تأیید می‌شوند و
قابل معامله‌اند. v4 بعداً از همان رابط adapter وارد می‌شود.

**Solana:** اسلات «به‌زودی» (COMING_SOON) با آداپتورهای Raydium / Meteora /
Orca — یک کار جداگانه و نیازمند استک کیف‌پول SPL و بازبینی جداگانه.

### راستی‌آزمایی DEX در لحظه (مهم‌ترین ایمنی آدرس‌ها)
ثابت‌های آدرس DEX **در هر لانچ، قبل از هر امضا**، روی زنجیره راستی‌آزمایی
می‌شوند:
1. فکتوریِ مدعی باید `getPair(anchorA, anchorB)` را به یک استخر **واقعی و
   غیرصفر** برگرداند (anchor = عمیق‌ترین مارکت آن DEX).
2. استخر باید `factory()` را به همان فکتوری برگرداند.
3. ذخایر استخر باید غیرصفر باشند.

اگر ثابتی اشتباه باشد، لانچ **مسدود** می‌شود (شکست ایمن) — هرگز استخر
غلط ساخته نمی‌شود. اسکریپت `scripts/verify-launch-dex.mjs` همین چک‌ها را
برای CI/اپراتور اجرا می‌کند.

## ۳. قوانین توکن (شفاف از قبل، دائمی روی زنجیره)

**توکن پایه (پیشنهادی):** عرضه ثابت، بدون mint، بدون pause، بدون سقف
انتقال، بدون مالیات، بدون سیاه‌فهرست. هر آنچه کاربر انتخاب می‌کند **حالا**
و **روی زنجیره** و **برای همیشه** مشخص می‌شود — هیچ «سوییچ پنهانی بعداً»
وجود ندارد.

**گزینه‌های پیشرفته (قدرت‌های مالک — هرکدام امتیاز ریسک را بالا می‌برد):**

| قابلیت | توضیح | ریسک |
|--------|-------|------|
| Mintable | مالک می‌تواند عرضه جدید بسازد | +۲۰ |
| Burnable | دارنده‌ها می‌توانند موجودی خود را بسوزانند | +۵ |
| Pausable | مالک می‌تواند انتقال‌ها را متوقف کند | +۱۵ |
| Max Wallet | مالک می‌تواند سقف هر کیف‌پول را تعیین/تغییر کند | +۱۰ |
| Max Tx | مالک می‌تواند سقف هر تراکنش را تعیین/تغییر کند | +۱۰ |

هیچ‌کدام از این‌ها مالیات، سیاه‌فهرست یا هانی‌پات نیستند و در قرارداد
`FBTBasicToken` هر کدام به‌صورت تابع جداگانه و شفاف پیاده‌شده‌اند.

## ۴. موتور ریسک (قطعی، ۰ تا ۱۰۰)

ریسک با **توابع ثابت و تست‌شده** محاسبه می‌شود — نه با مدل زبانی. ورودی
یکسان = امتیاز یکسان، روی همه دستگاه‌ها، بدون شبکه. AI فقط می‌تواند یافته‌ها
را **توضیح** دهد؛ نه امتیاز را کم کند و نه لانچ را تأیید کند.

بازه‌ها: ۰–۲۰ پایین · ۲۱–۴۰ متوسط · ۴۱–۶۰ بالا · ۶۱–۸۰ زیاد · ۸۱–۱۰۰ بحرانی

**گیت‌های فوری (invariant، نه نظریه):**
- DEX روی زنجیره تأیید نشد → **مسدود**
- فکتوری FBT روی شبکه دیپلوی نشده → **مسدود**

امتیاز «زیاد/بحرانی» به‌طور پیش‌فرض مسدود نمی‌کند؛ اما UI کاربر را مجبور
می‌کند **نماد توکن را تایپ** کند (تأیید صریح) و همهٔ یافته‌ها را ببیند.

یافته‌ها در دو جهت صادقانه‌اند: مثلاً «LP در کیف‌پول خودتان می‌ماند — بدون
قفل، بدون واسطه» و «بدون مالیات، بدون سیاه‌فهرست — با طراحی قرارداد» هم به‌عنوان
یافتهٔ مثبت نمایش داده می‌شوند.

## ۵. کارمزد (شفاف، قبل از امضا)

| کارمزد | فاز ۱ |
|--------|-------|
| لانچ | **۰٪** |
| سواپ روی استخر | ۰٫۷۰٪ (کارمزد موجود پلتفرم) |
| پروتکلی | ۰٪ |

کارمزد دقیق با واحد کاربر در **مرحلهٔ مرور** و قبل از هر امضا نشان داده
می‌شود. اگر روزی کارمزد غیرصفر شد، در تراکنش جداگانه و با امضای صریح کاربر
و به آدرس عمومی منتشرشده پرداخت می‌شود — هرگز داخل فراخوان توکن/استخر.

## ۶. جریان کاربر (۵ مرحله)

1. **شبکه** — انتخاب شبکه + وضعیت آماده‌بودن فکتوری + راستی‌آزمایی زندهٔ DEX.
2. **توکن** — نام، نماد، اعشار، عرضه، لوگو (فقط محلی)، توضیح.
3. **قوانین** — پایه یا پیشرفته + پیش‌نمایش زندهٔ امتیاز ریسک.
4. **نقدینگی** — ارز جفت‌واری، مقادارها، قیمت اولیه، اسلیپیج.
5. **مرور و لانچ** — جمع‌بندی کامل (عرضه، قیمت، نقدینگی، کارمزد، تعداد
   امضاها) + پنل ریسک + سیمولیشن + تأیید صریح (در ریسک بالا) + **لانچ**.

### اجرای چندمرحله‌ای (دوفازی صادقانه)
- **فاز ۱:** ساخت توکن (`createToken` روی فکتوری FBT).
- پس از تأیید تراکنش، آدرس **واقعی** توکن از event `TokenCreated` خوانده
  می‌شود.
- **فاز ۲:** بایت‌های استخر/نقدینگی **با آدرس واقعی** آماده می‌شوند
  (approve توکن → approve ارز → createPair در صورت نیاز → addLiquidity).
  استخر از قبل موجود است؟ `createPair` ساقط می‌شود (چک زنده قبل از امضا).

### شکست صادقانه (قانون مهم)
اگر توکن ساخت شد ولی استخر شکست، سیستم **دقیقاً همان را** گزارش می‌کند:

```
توکن: SUCCESS (آدرس) · استخر: FAILED (مرحلهٔ خراب، دلیل)
بازیابی: retry-pool  ←  توکن دوباره ساخته نمی‌شود؛ فقط فاز استخر تکرار می‌شود
```

state machine:
`DRAFT → CONFIGURED → SIMULATING → SIMULATED → AWAITING_CONFIRMATION →
SIGNING → SUBMITTED → CONFIRMING → VERIFIED → LIVE`
به‌علاوه `FAILED / RETRYABLE / CANCELLED / EXPIRED`.

**LIVE فقط بعد از VERIFIED** است: یعنی همهٔ فکت‌ها (نام، نماد، اعشار، عرضه،
ذخایر استخر، موجودی LP) از زنجیره **بازخوانی** شده و با مقادیر امضاشده
مطابق‌اند. در استخر تازه‌ساخته، ذخایر باید در بازهٔ
`[حداقلِ امضا، ۱٫۰۲×مقدارِ امضا]` باشند (رصد front-run).

## ۷. API (همه در `server/launch.js`)

| Endpoint | توضیح |
|----------|-------|
| `GET /api/launch/config` | شبکه‌ها، registry فکتوری‌ها، کارمزدها، بیانیهٔ غیرامانی |
| `GET /api/launch/prepare` | بایت‌های هر فاز + ریسک + وضعیت DEX (stateless) |
| `GET /api/launch/verify` | بازخوانی فقط‌خواندنی از زنجیره (توکن/استخر/LP) |
| `POST /api/launch/record` | رکورد عمومی (فقط فیلدهای غیرحساس)؛ بدون store پایدار → **503** |
| `GET /api/launch/records/:chainId` | رکوردهای عمومی یک شبکه |

API **هرگز** امضا نمی‌کند، ارسال نمی‌کند و چیزی نگه نمی‌دارد.

### متغیرهای محیطی
```
FBTLAUNCH_FACTORY_<CHAINID>=0x…      # آدرس فکتوری FBT روی شبکه (الزامی برای لانچ)
FBTLAUNCH_DEX_FACTORY_<CHAINID>=0x…  # (اختیاری) override فکتوری DEX
```
دیپلوی فکتوری:
```
node scripts/compile-launch.mjs
DEPLOYER_PRIVATE_KEY=0x… RPC_URL=https://… CHAIN_ID=56 \
  node scripts/deploy-launch-factory.mjs
# سپس آدرس چاپ‌شده را در FBTLAUNCH_FACTORY_56 بگذارید
```

## ۸. SDK

`sdk/fbt-launch.mjs` — کلاینت نازک و **کیف‌پول-مستقل** (browser + Node 18+):

```js
import { FBTLaunch } from './sdk/fbt-launch.mjs';

const launch = new FBTLaunch({
  apiBase: 'https://fbt.example.com/api',
  signer: wallet.getSigner(),        // امضا در کیف‌پول کاربر
  provider: wallet.getReadProvider(),
  address: wallet.address
});

const plan = await launch.prepare({ chainId: 56, name: 'FBT Gold', symbol: 'FBTG',
  decimals: 18, supply: '1000000000',
  quote: { symbol: 'USDT', address: '0x…', decimals: 6 },
  tokenAmount: '100000', quoteAmount: '10000' });

const result = await launch.run(plan.plan, { onStep: s => console.log(s) });
// result.state: 'CONFIRMED' | 'RETRYABLE' | 'FAILED' | 'CANCELLED'
```

SDK همان بایت‌هایی را امضا می‌کند که API تولید کرده — چون هر دو از یک
سازندهٔ مشترک (calldata.js) استفاده می‌کنند.

## ۹. تست‌ها و چک‌های ایمنی

- `test/launch-probe.mjs` — ~۷۰ ادعا: اعتبارسنجی spec، بیت‌مپ‌ها، موتور
  ریسک + گیت‌ها، کارمزدها، **دقت بایتی calldata** (decode و مقایسه با
  intent)، state machine کامل، شکست ناقص، sanitization تاریخچه، آرتیفکت‌ها.
- `scripts/verify-launch-dex.mjs` — راستی‌آزمایی registry DEX روی زنجیره‌ها.
- `scripts/deploy-launch-factory.mjs` — دیپلوی + verify فکتوری (bytecode
  match + probe رابط).

## ۱۰. محدودیت‌های صادقانهٔ فاز ۱

- **Solana:** اسلات «به‌زودی» (نیازمند استک جداگانه).
- **IPFS/Arweave:** فاز ۱ متادیتا را محلی نگه می‌دارد؛ آپلود عمومی بعداً.
- **سیمولیشن سمت سرور:** سیمولیشن (estimateGas/eth_call) سمت کاربر/SDK
  انجام می‌شود؛ API فقط plan و verify دارد.
- **v4/LI.FI/thirdweb:** بعداً از آداپتورها — هیچ‌کدام SPOF نیستند و
  هسته به هیچ‌کدام وابسته نیست.
