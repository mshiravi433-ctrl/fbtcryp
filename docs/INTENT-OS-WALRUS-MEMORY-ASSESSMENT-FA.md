# ارزیابی فنی: Walrus Memory (MemWal) برای Intent OS

**تاریخ:** ۲۰۲۶-۱۰-۰۲ · **نوع سند:** ارزیابی تصمیم — **بدون هیچ تغییر کد**
**پرسش:** آیا می‌شود از لایهٔ حافظهٔ بلاک‌چینی Walrus Memory (MemWal) برای اپ هوش مصنوعی Intent OS استفاده کرد و کارآمدی را بالا برد؟

---

## ۱. پاسخ کوتاه

**بله، اما نه به‌عنوان جانشین حافظهٔ فعلی؛ در دو جای مشخص و با سه شرط.**

- **بله درست:** «حافظهٔ معنایی بلندمدت کاربر» — ترجیج‌ها، اهداف، تصمیم‌ها و فکت‌های گفتگو — و «حافظهٔ مشترک بین ایجنت‌ها» با قابلیت اثبات‌پذیری.
- **نه درست:** دارایی، موجودی، سفارش، پوزیشن و هر وضعیت مالی قطعی. (خود مستندات MemWal می‌گوید recall معنایی برای بازیابی یک رکورد ساختاریافتهٔ معتبر قابل اتکا نیست و به issue #247 ارجاع می‌دهد.)
- **نه قبل از عبور از سه گیت:** (۱) تأخیر recall در مسیر بحرانی پاسخ، (۲) مدل اعتماد و حریم خصوصی (relayer پیش‌فرض متن خام را می‌بیند و آن را به OpenAI می‌دهد)، (۳) سهمیه و rate-limit حساب مشترک اپراتور.

برد اصلی «کارآمدی» این است: امروز هر نوبت چت به‌جای حافظهٔ واقعی، **۸ پیام آخر + یک خلاصهٔ ۶۰۰ کاراکتری** را حمل می‌کند و آن خلاصه هم در بازخوانی عملاً خالی برمی‌گردد (بند ۳-ب). یعنی هم توکن مصرف می‌شود، هم حافظه کار نمی‌کند. MemWal برای همین شکاف ساخته شده.

## ۲. این سرویس دقیقاً چیست (فقط چیزهای مستند)

| موضوع | واقعیت |
|---|---|
| چیستی | Walrus Memory (نام SDK: **MemWal**) لایهٔ حافظهٔ معنایی برای ایجنت‌های AI روی شبکهٔ ذخیره‌سازی **Walrus** (روی Sui). لانچ عمومی: ۳ ژوئن ۲۰۲۶؛ پیش‌نمایش از مارس ۲۰۲۶. |
| سطح‌ها | SDK تایپ‌اسکریپت (`@mysten-incubation/memwal`) + SDK پایتون (`memwal`) + سرور MCP (نقل‌وانتقال stdio و HTTP/SSE) |
| امنیت داده | متن حافظه با **Seal** رمزنگاری می‌شود، در Walrus به‌صورت blob ذخیره می‌شود؛ مالکیت و کلیدهای delegate روی Sui و با قرارداد هوشمند اعمال می‌شود؛ رابط، هدرهای امضاشدهٔ **Ed25519** می‌خواهد (`x-public-key`, `x-signature`, `x-timestamp` با پنجرهٔ ۵ دقیقه, `x-nonce`). |
| معماری داخلی | relayer (Rust/Axum) + sidecar (TS: Seal + Walrus) + **PostgreSQL + pgvector** برای ایندکس برداری + Sui RPC. یعنی «جست‌وجو» متمرکز است، «ذخیره‌سازی» غیرمتمرکز. |
| امکانات | `remember` / `recall` / `restore` / `analyze` (استخراج فکت با LLM) / `ask` / نسخهٔ manual (رمزنگاری و embedding سمت کلاینت) |
| مدل‌های پیش‌فرض | embedding: `text-embedding-3-small` (۱۵۳۶ بُعد) · تحلیل/پاسخ: `gpt-4o-mini` — هر دو سمت relayer |
| محدودیت پیش‌فرض relayer میزبان | **۶۰ point در دقیقه** و **۵۰۰ point در ساعت** به‌ازای هر حساب (Sui address) · **۳۰ point در دقیقه** به‌ازای هر delegate key · سهمیهٔ ذخیره‌سازی **۱ گیگابایت** برای هر حساب. وزن‌ها: `remember`=۵، `analyze`=۱۰، `recall`=۱، `ask`=۲، `restore`=۳. |
| قیمت | در دورهٔ لانچ: «برای سازندگان رایگان، با اعمال محدودیت مصرف، قیمت‌گذاری ممکن است تغییر کند». لایهٔ ذخیره‌سازی Walrus: **$۰.۰۲۳ به‌ازای هر گیگابایت در ماه**. |
| حالت اضافی | self-hosting کامل relayer (Postgres+pgvector، کلید Sui، کلید OpenAI، توکن sidecar) که در آن **همهٔ محدودیت‌ها و سهمیه‌ها قابل تنظیم‌اند** |

### چهار مدل اعتماد (مهم‌ترین بخش برای FBT)

| حالت | relayer چه می‌بیند | مناسب چه کسی |
|---|---|---|
| relayer میزبان (پیش‌فرض) | متن خام، embedding، خروجی رمزگشایی‌شده | نمونه‌سازی سریع |
| self-host | همان، ولی در زیرساخت خودت | کنترل کامل داده |
| TEE (Nautilus) | متن خام فقط داخل enclave تأییدشده | حد وسط |
| **manual client flow** | فقط ciphertext + بردار آمادهٔ embedding؛ هرگز متن خام | حریم خصوصی حداکثری |

## ۳. Intent OS امروز چه حافظه‌ای دارد (شواهد داخل همین ریپو)

### الف) لایه‌های موجود

| لایه | فایل | محل ذخیره | ماندگاری |
|---|---|---|---|
| Working / Session / Long-term | `src/lib/intent-ai/os/memoryEngine.js` | localStorage | **فقط همین دستگاه/مرورگر** |
| Semantic Memory v7 (fact/preference/goal/task) | `src/lib/intent-ai/os/upgrade7/semanticMemory.js` | localStorage | فقط همین دستگاه |
| L1/L2/L3 | `src/lib/intent-ai/os/upgrade6/memoryV2.js` | localStorage | فقط همین دستگاه |
| حافظهٔ سروری | `server/aiIntentOS.js` → `readMemory` / `appendMemory` روی `server/store.js` | Vercel Blob، و اگر توکن نباشد **Map درون‌پروسه** | TTL پیش‌فرض ۳۰ روز (`STORE_EPHEMERAL_TTL_MS`)؛ بدون `BLOB_READ_WRITE_TOKEN` با هر cold start پاک می‌شود |
| Context هر نوبت | `server/aiIntentOS.js` حدود خط ۱۵۸۰ | — | `messages.slice(-8)` |
| حافظهٔ مرکزی (Memory OS، ۸ نوع) | `src/lib/central/memory.js` | درون‌حافظه‌ای/سمت کلاینت | محدود به عمر تب |

در `src/lib/intent-ai/` حدود **۱۰۶ ارجاع `localStorage`** وجود دارد؛ یعنی بخش بزرگی از «شخصیت و حافظهٔ» Intent OS به دستگاه گره خورده است.

### ب) دو شکاف قابل اندازه‌گیری

1. **سقف پنجرهٔ حافظه:** هر درخواست چت فقط ۸ پیام آخر (هر پیام حداکثر ۱۲۰۰ کاراکتر) را می‌بیند.
2. **خلاصهٔ سروری هرگز بازخوانی نمی‌شود:** نویسنده فیلد را `summary` ذخیره می‌کند (`appendMemory`، خط ۵۵۹)، ولی خواننده‌ها `conversationSummary` می‌خوانند:
   - `server/aiIntentOS.js:475` (ساخت context) → همیشه رشتهٔ خالی
   - `src/components/IntentAIUnified.jsx:5300` (`aiMemory()` در استارتاپ) → همیشه undefined
   - تنها مسیری که کار می‌کند، پژواک همان پاسخ است (خطوط ۱۶۴۱ و ۲۱۹۷)، نه نشست بعدی.

   یعنی امروز «تداوم بین نشست‌ها» در عمل وجود ندارد؛ هر بار از صفر شروع می‌شود. این تنها دلیل کافی برای بررسی یک لایهٔ حافظهٔ واقعی است — مستقل از اینکه Walrus انتخاب شود یا نه.

## ۴. جاهایی که واقعاً کارآمدی را بالا می‌برد

| # | گلوگاه امروز | چیزی که MemWal می‌دهد | اثر عملی |
|---|---|---|---|
| ۱ | context هر نوبت سنگین است (خلاصه + ۸ پیام + پورتفویو و بازار و خبر) | `recall` با `limit` کوچک (۳ تا ۵) و وزن‌دهی `importance`/`recency` | کاهش توکن ورودی هر نوبت و کوتاه‌شدن مسیر ساخت prompt |
| ۲ | حافظه به دستگاه گره خورده (۱۰۶ ارجاع localStorage) | حافظه به «حساب» گره می‌خورد، نه مرورگر؛ مسیر بازگشت کاربر در مستندات صریح است («فقط کلید delegate در مرورگر قبلی جا می‌ماند») | تعویض موبایل/نصب مجدد/وب↔اپ، حافظه را از دست نمی‌دهد |
| ۳ | ادامهٔ عملیات‌ها (Operation continuation) روی خلاصهٔ رشته‌ای | بازیابی معنایی «این کار را قبلاً ساختیم/تصویب کردیم» | نرخ «یادم نمی‌آید» و دوباره‌پرسیدن پایین می‌آید |
| ۴ | ادعاهای AI قابل ارجاع نیستند | هر حافظه = یک `blob_id` قابل استناد روی Walruscan + مالکیت onchain | هم‌راستا با فرهنگ فعلی پروژه (Proof-of-Execution receipt، transparency log، anchor) — «چرا AI این حرف را زد؟» جواب مستند می‌گیرد |
| ۵ | چند ایجنت، حافظهٔ جدا و بدون اشتراک | namespace جدا برای هر ایجنت زیر یک حساب، با اشتراک‌گذاری انتخابی | مسیر واقعی برای `agentMemory` / `agentProtocol` / شورای ایجنت‌ها بدون ساختن زیرساخت جدید |
| ۶ | حافظه با پاک‌شدن ایندکس از بین می‌رود | `restore` یعنی «حافظه از روی زنجیره بازساخته می‌شود» | بازیابی واقعی فاجعه (disaster recovery) نه فقط بکاپ فایل |
| ۷ | تولید و نگهداری حافظه دستی است | `analyze` فکت‌ها را از متن بلند استخراج و جدا ذخیره می‌کند | ورود «گفتگوی قدیمی» به حافظه بدون کار دستی |

## ۵. جاهایی که نباید استفاده شود یا ریسک جدی دارد

| ریسک | توضیح | توصیه |
|---|---|---|
| **وضعیت مالی قطعی** | recall معنایی برای رکورد ساختاریافته قابل اعتماد نیست (خود داکیومنت، issue #247) | موجودی/سفارش/پوزیشن در همان مسیر فعلی (خواندن زنجیره) بماند؛ هرگز AI از حافظه نقل نکند |
| **متن خام و OpenAI** | relayer میزبان متن خام را می‌بیند و embedding/تحلیل را به OpenAI می‌دهد؛ embedding با `text-embedding-3-small` و `analyze` با `gpt-4o-mini` | عبور اجباری از `sanitize()` موجود (`src/lib/central/memory.js`: الگوهای FORBIDDEN/KEYLIKE) پیش از هر نوشتن + فیلتر PII + تصمیم صریح دربارهٔ OpenAI |
| **دسترس‌پذیری برای کاربران ایران** | endpoint میزبان `relayer.memory.walrus.xyz` و کلید OpenAI؛ FBT عمداً OpenAI را از gateway خودش حذف کرده | تست دسترسی از محیط واقعی deploy قبل از هر تعهد محصولی |
| **تأخیر** | `recall` = embedding + جست‌وجوی pgvector + دانلود از Walrus + رمزگشایی Seal؛ مستندات عدد نمی‌دهد (گزارش ثالث ~۱.۵–۳ ثانیه P95، تأییدنشده) | هرگز در مسیر بحرانی: race با deadline (همان الگوی `ctxDeadline` ۸ ثانیه‌ای موجود)، نوشتن fire-and-forget، کش داغ روی سمت FBT |
| **وابستگی به Sui/relayer ثالث** | قطعی حدود ۶:۴۴ ساعتهٔ Sui در مه ۲۰۲۶ نمونه است (منبع ثالث) | حافظهٔ محلی همان دستگاه مرجعِ اول بماند؛ Walrus «لایهٔ دوم» باشد نه تک‌نقطه |
| **سقف عمر blob** | blob‌ها برای تعداد epoch محدود اجاره می‌شوند (self-host: پیش‌فرض ۳ روی mainnet، سقف ۱۵) | باید روشن شود تمدید epoch در relayer چگونه مدیریت می‌شود؛ وگرنه حافظه بی‌صدا می‌پوسد |
| **سهمیه و rate limit** | مدل multi-tenant با **یک حساب اپراتور** یعنی کل اپ در ۵۰۰ point/ساعت و ۱ گیگابایت شریک است (~۱۰۰ `remember` در ساعت برای همهٔ کاربران) | برای پایلوت کافی است؛ برای تولید انبوه یکی از سه مسیر: self-host (محدودیت‌ها قابل تنظیم)، حساب به‌ازای هر کاربر (نیازمند هویت Sui که کاربران FBT ندارند)، یا جداکردن حسابداری حافظه از محصول اصلی |
| **کلید و بلوغ محصول** | delegate key یک credential سروری ارزشمند است؛ محصول در وضعیت لانچ/رایگان با محدودیت و «قیمت‌گذاری ممکن است تغییر کند» | کلید فقط در env سرور، برنامهٔ rotate/revoke، و آمادگی برای تغییر قیمت/مدل |
| **بار ایجنت‌های خودکار** | مانیتورها و ایجنت‌های FBT می‌توانند نقطه‌های نرخ را بسوزانند | namespace و بودجهٔ نقطه‌ای جدا برای automation، با سقف سخت |

## ۶. سه معماری ممکن (بار انتخاب)

| | A) relayer میزبان، حساب اپراتور، مسیر SDK | B) حساب برای هر کاربر | C) self-host یا manual flow |

## ۸. سنجه‌هایی که باید قبل و بعد اندازه گرفته شود

- **توکن ورودی هر نوبت** (قبل/بعد) — بزرگ‌ترین ادعای «کارآمدی» است و باید عدد داشته باشد.
- **p50/p95 تأخیر پاسخ چت** و **p50/p95 تأخیر recall** به‌تفکیک نوع پرسش.
- **نرخ ادامه‌دهی درست عملیات** (کاربر می‌گوید «همان را ادامه بده» و پاسخ درست است).
- **نرخ «یادم نمی‌آید» / سؤال تکراری** روی نمونهٔ واقعی گفتگوها.
- **نرخ fallback** (چند درصد نوبت‌ها بدون حافظهٔ Walrus پاسخ گرفتند).
- **هزینهٔ ماهانه به‌ازای ۱۰۰۰ کاربر فعال** (ذخیره‌سازی + embedding + LLM؛ ترافیک Walrus مستقل از بار FBT است).

---

## ۹. برآورد هزینهٔ خام (با فرض‌های صریح)

- ۱۰۰۰ کاربر فعال × ۵۰ کیلوبایت حافظهٔ خام ≈ ۵۰ مگابایت → در نرخ Walrus حدود **۰.۰۰۱ دلار در ماه**؛ هزینهٔ واقعی جای دیگری است: embedding/LLM سمت relayer، gas ایجاد حساب، و نقطه‌های rate-limit.
- قیمت دورهٔ لانچ «رایگان با محدودیت» است؛ برای تولید باید فرض «قیمت آینده نامعلوم» را در برنامه بگذاری.
- گزینهٔ C هزینهٔ ثابت سرور + Postgres دارد (کاملاً قابل برآورد، برخلاف حالت میزبان).

---

## ۱۰. آنچه در این ارزیابی تأیید نشده (ریسک دانستن)

1. عدد رسمی تأخیر recall در مستندات نیست.
2. قیمت آیندهٔ Walrus Memory و سقف‌های دقیق حساب اپراتور در محصول نهایی مشخص نیست.
3. دسترسی پایدار به relayer و به OpenAI از محیط کاربران هدف تأیید نشده.
4. مدیریت تمدید epoch (عمر blob) در relayer میزبان شفاف نیست.
5. کیفیت embedding فارسی روی `text-embedding-3-small` برای حافظهٔ مالی سنجیده نشده — این باید در فاز ۰ تست شود.

---

## ۱۱. جمع‌بندی

MemWal یک راه‌حل بالغ برای «حافظهٔ معنایی ایجنت» است و دقیقاً روی دردی می‌نشیند که Intent OS امروز دارد (پنجرهٔ ۸ پیامی، حافظهٔ دستگاه‌محور، و خلاصه‌ای که بازخوانی نمی‌شود). اما «کارآمدی» اینجا دو لبه دارد: کاهش توکن و افزایش تداوم در یک طرف، و افزودن یک وابستگی شبکه‌ای با تأخیر و مدل اعتماد جدید در طرف دیگر.

پس مسیر درست این است: **۱ روز سنجش، بعد یک پایلوت محدود روی پروفایل بلندمدت با fallback کامل، و بعد تصمیم دربارهٔ مقیاس و حریم خصوصی.** وضعیت مالی کاربر هرگز به این لایه سپرده نشود.
