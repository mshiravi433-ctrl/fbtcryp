# آپگرید اسمارت‌مانی — فاز ۳ (۲۰۲۶-۱۰-۲۵)

ادامه‌ی `docs/2026-10-25-smart-money-upgrade-fa.md` (فاز ۱) و
`docs/2026-10-25-smart-money-upgrade-phase2-fa.md` (فاز ۲). درخواست:
«فاز ۳ را شروع کن» — یعنی دو قلم باقی‌مانده: **سواپ‌های مظنه‌ی نیتیو** و
**دفتر جفت‌سواپ سولانا**.

## تصمیم مرکزی: اول مشاهده، بعداً (اگر کامل شد) رأی

هر دو مسیر در این فاز **observed-only** هستند: ردیف‌ها در فیلد جدا‌ی
`observedSwaps` برمی‌گردند، `classification: 'observed-only'` و
`admission: 'excluded-from-verified-score-and-consensus'` دارند و در UI
با برچسب «بدون رأی در امتیاز و اجماع» دیده می‌شوند. مسیر قدیمی یک ذره
هم عوض نشده است:

- `analyzePerformance` همچنان فقط سواپ‌های استیبل‌مظنه‌ی
  `paired-explorer-transfers` را به FIFO می‌دهد.
- اجماع و ایندکس همچنان فقط همان evidence و `verifiedSwaps` را می‌پذیرند.
- برای سولانا `verifiedSwaps: []`، امتیاز `null` و وضعیت `UNAVAILABLE`
  می‌ماند؛ حتی وقتی ردیف مشاهده‌شده وجود دارد.

یعنی فاز ۳ «داده‌ی بیشتر با برچسب درست» تحویل می‌دهد، نه «صلاحیت و
اجماع با تعریف ضعیف‌تر».

## ۱) EVM: سواپ‌های مظنه‌ی نیتیو‌ی رپ‌شده

تابع جدید `reconstructNativeQuoteSwaps` در `performance.js`:

- فقط زنجیره‌هایی که لیست سفید استیبل‌کوین تأییدشده دارند؛ آدرس
  WETH/WBNB/WMATIC/WAVAX و مانند آن از رجیستری `chainsLite` خوانده
  می‌شود (نه از روی سمبل — هر کسی می‌تواند توکنی به نام WETH بسازد).
- همان سخت‌گیری دفتر تأییدشده: تراکنش موفق، شاهد DEX/متد سواپ، **دقیقاً
  دو** طرف انتقال برای کیف‌پول، دو جهت مخالف، یک طرف قرارداد نیتیو‌ی
  رپ‌شده و یک طرف توکن هدفِ غیراستیبل، با اختلاف زمانی حداکثر دو دقیقه.
  باندل چنددارایی، تراکنش ناموفق و نیتیو→استیبل رد می‌شوند.

### قیمت در لحظه‌ی تراکنش

یافته‌ی آغاز فاز: `historicalPriceFn` موجود فقط سری روزانه است (نزدیک‌ترین
نقطه تا سه روز دورتر). استفاده از آن برای ارزش‌گذاری طرف نیتیو همان
«دروغ دقت» بود؛ پس دست نخورده مانده و یک مسیر جدا ساخته شد:

- `historicalHourlyPriceFn` از `market_chart/range` کوین‌گکو می‌خواند
  (طبق مستندات کوین‌گکو، گرانولاریته‌ی خودکار برای بازه‌های تا ۹۰ روز
  ساعتی یا ریزتر است)، اما به برچسب اعتماد نمی‌کند: `intradayPriceLookup`
  فاصله‌ی میانه‌ی نقاط برگشتی را می‌سنجد و سری‌ای را که ساعتی‌ـ‌ یا
  ریزتر نیست (از جمله سری روزانه) کاملاً رد می‌کند.
- برای هر سواپ، نزدیک‌ترین نقطه باید **حداکثر یک ساعت** با زمان تراکنش
  فاصله داشته باشد؛ نقطه‌ی استفاده‌شده با `{usd, at, granularity, source}`
  روی خود ردیف ثبت می‌شود.
- اگر قیمت ساعتی قابل‌اثبات نباشد، ردیف با مقدار واقعی نیتیو
  (`quoteAmount`) می‌ماند ولی `valueUsd` و قیمت اجرا `null` هستند — مقدار
  دلاری ساخته نمی‌شود. وضعیت این منبع هم در `sources.nativeQuotePricing`
  گزارش می‌شود (فقط وقتی ردیف نیتیوی وجود داشته باشد).

## ۲) سولانا: دیکود از دلتای موجودی توکن

قبل از فاز ۳ سولانا فقط امضا و موجودی داشت. حالا:

- منبع داده‌ی جدید `solTransactions` حداکثر ۲۵ امضای اخیر و موفق را با
  `getTransaction` ‏(`jsonParsed`، `maxSupportedTransactionVersion: 0`)
  می‌خواند؛ با هم‌روندی محدود (۵) و سقف زمانی ۳٫۵ ثانیه داخل بودجه‌ی
  خواندن کیف‌پول. خروجی همیشه شمارش دقیق دارد (`requested / attempted /
  fetched / failed / unattempted`) و خواندن ناقص `partial` برچسب می‌خورد.
- دیکودر جدید `server/smartMoney/solanaSwaps.js` فقط وقتی ردیف می‌سازد که
  در یک تراکنشِ موفق، تغییر خالص موجودی‌ی **متعلق به خود کیف‌پول**
  دقیقاً روی **دو مینت** باشد، دو جهت مخالف داشته باشند، یکی USDC/USDT
  canonical (با آدرس مینت، نه سمبل) باشد و یک برنامه‌ی شناخته‌شده‌ی DEX
  یا Jupiter در دستورهای بیرونی/درونی حاضر باشد.
- دلتاها روی مقادیر خام با `BigInt` حساب می‌شوند (قبل از تبدیل به عدد
  اعشاری)، پس موجودی‌های بزرگ‌تر از `Number.MAX_SAFE_INTEGER` هم دلتای
  دقیق می‌دهند.
- موارد رد: تراکنش ناموفق، برنامه‌ی ناشناخته، سه مینت یا بیشتر، دلتاهای
  هم‌جهت، هدفِ WSOL، و هر ردیف موجودی‌ی بدون `owner`. مالک نامعلوم از روی
  ایندکس حساب حدس زده نمی‌شود، چون همان ردیف می‌توانست مینتِ سوم کیف‌پول
  باشد و اثبات «دقیقاً دو مینت» را باطل کند.

### چرا سولانا هنوز رأی نمی‌دهد

دو دلیل فنی صادقانه: نمونه فقط تا ۲۵ تراکنش اخیر است (دفتر کامل و مرتب
برای FIFO نیست) و `pre/postTokenBalances` اثر همه‌ی فیل‌های یک تراکنش را
**خالص** می‌کند. پس هر ردیف یک «اثر جفت‌شده‌ی مشاهده‌شده» است، نه رسید
بستن موقعیت.

## ۳) نمایش در صفحه‌ی کیف‌پول

بخش تازه‌ی «سواپ‌های مشاهده‌شده» زیر دارایی‌ها و جدا از فعالیت اخیر:
جهت خرید/فروش، مقدار و توکن هدف، طرف مظنه (و مقدار دلاری فقط اگر روی
ردیف واقعاً باشد)، برای سولانا نام برنامه‌ی DEX و شمارش نمونه‌ی خوانده‌شده
(مثلاً «۱۷ از ۲۵»)، و دکمه‌ی رسید به اکسپلورر زنجیره (سولانا: Solscan).
رنگ و برچسب بخش عمداً از لایه‌ی تأییدشده جدا است و در موبایل هم برچسب
«بدون رأی» پنهان نمی‌شود.

## پاسخ API (افزودنی)

```jsonc
{
  "verifiedSwaps": [ /* فقط استیبل‌مظنه، مثل قبل */ ],
  "observedSwaps": [ /* فاز ۳: native EVM یا Solana */ ],
  "swapEvidence": {
    "verified":   { "count": 0, "classification": "verified", "evidence": "paired-explorer-transfers" },
    "observedOnly": { "count": 0, "classification": "observed-only",
                      "admittedToScore": false, "admittedToConsensus": false, "basis": "…" }
  }
}
```

مصرف‌کننده‌های قبلی بی‌تغییر کار می‌کنند؛ هیچ فیلد قدیمی حذف یا
بازتعریف نشده است.

## قدم بعدی (فاز ۴ احتمالی): ارتقا به کلاس تأییدشده

هیچ‌کدام از دو دفتر خودکار ارتقا پیدا نمی‌کنند. شرط‌های لازم:

- **نیتیو:** پوشش قیمت ساعتی روی نمونه‌های واقعی سنجیده شود؛ دفتر یکپارچه‌ی
  استیبل+نیتیو بدون دوباره‌شماری لات‌های یک توکن طراحی شود و روی
  کیف‌پول‌های معلوم بازپخش (replay) شود.
- **سولانا:** صفحه‌بندی کامل امضاها (نه فقط ۲۵ تای اخیر)، دیکود در سطح
  دستور برای جدا کردن فیل‌های یک تراکنش، و فیكسچر از تراکنش‌های واقعی
  هر برنامه‌ی DEX.
- تا آن روز، هر ارتقا بدون این اثبات‌ها یعنی برگشتن به همان چیزی که
  فاز ۱ حذف کرد.

منابع بیرونی: مستندات کوین‌گکو برای گرانولاریته‌ی خودکار
(`docs.coingecko.com/reference/coins-id-market-chart-range`) و مستندات
RPC سولانا برای ساختار `pre/postTokenBalances` و فیلد `owner`
(`solana.com/docs/rpc/http/gettransaction`).
