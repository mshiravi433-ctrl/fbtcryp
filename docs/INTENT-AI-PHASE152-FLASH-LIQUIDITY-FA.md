# Intent OS — فاز ۱۵۲: Flash Liquidity (آربیتراژ با فلش لان بدون وثیقه)

> وضعیت پیاده‌سازی: **کنترل‌پلن، ریاضیِ بهینه‌سازی، اسکنر، خط لوله ۹ مرحله‌ای، API خشک (dry-run)،
> صفحه `/#/flash-liquidity` و قرارداد مرجع کامپایل‌شده تکمیل شده‌اند.**
> این عبارت به معنی فعال بودن اجرای خودکار، سود تضمینی یا وام نقدی برای خرج‌کردن نیست.
> اجرای واقعی به شبیه‌سازی موفق، قرارداد مستقل‌ممیزی‌شده و امضای صریح کیف پول نیاز دارد.

## ۱) فلش لان چیست و چه چیزی نیست

در فلش لان، کاربر مثلاً ۱۰ میلیون USDC را **بدون وثیقه** قرض می‌گیرد، اما یک شرط سخت وجود دارد:

> اصل وام + کارمزد باید **در همان تراکنش بلاکچین** برگردد؛ در غیر این صورت کل تراکنش
> revert می‌شود و گازِ خرج‌شده هم از دست می‌رود.

پس فلش لان:

- ✗ پول رایگان نیست.
- ✗ اعتبار قابل خرج‌کردن یا «وام نقدی» برای کاربر نیست.
- ✗ سود تضمین‌شده نمی‌دهد.
- ✓ سرمایهٔ موقتِ داخل یک تراکنش است؛ کاربرد واقعی‌اش arbitrage، liquidation و
  collateral swap است.

مسیر نمونه:

```text
Aave/Balancer → 10M USDC → DEX 1 → DEX 2 → 10.015M USDC → بازپرداخت → سود
اگر سود کافی نباشد:  Transaction → REVERT
```

## ۲) معماری در FBT

```text
                 FBT Intent OS
                       │
                       ▼
          AI Opportunity Scanner          ← src/lib/intent-ai/flashLiquidity.js
                       │
              Flash Liquidity Router     ← انتخاب Provider + حجم بهینه
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        Aave V3      Balancer     منابع دیگر (فازهای بعد)
     flashLoanSimple  Vault.flashLoan
          │            │            │
          └────────────┼────────────┘
                       ▼
              MEV/Execution Policy       ← فقط ارسال خصوصی؛ ممپول عمومی رد می‌شود
                       │
                 DEX Route (hops)        ← minOut برای هر hop + deadline
                       │
                       ▼
              Atomic Settlement          ← همه یا هیچ؛ چک on-chain حداقل سود
                       │
                       ▼
        قرارداد مرجع: contracts/FlashLiquidityRouter.sol
```

### Providerها

| Provider | ورودی | Callback | کارمزد پیش‌فرض | چند دارایی؟ |
|---|---|---|---|---|
| Aave V3 | `flashLoanSimple()` | `executeOperation()` | ۵ bps (۰.۰۵٪) | تک‌دارایی |
| Balancer Vault | `flashLoan()` | `receiveFlashLoan()` | ۰ bps | چند دارایی |

**مهم — fail-closed بودن آدرس‌ها:** فقط آدرس‌های `verified: true` برای ساخت
آماده‌سازیِ اجرا مجازند. در این نسخه آدرس Vault بالانسر (یکسان روی همهٔ زنجیره‌های V2)
و Aave Pool اتریوم تأیید شده‌اند؛ بقیهٔ زنجیره‌ها در رجیستری با `verified: false`
هستند و برنامه‌ریز روی آن‌ها با `PROVIDER_ADDRESS_UNVERIFIED` رد می‌شود — هرگز
fail-open نمی‌شود. آدرس‌ها باید از مستندات رسمی هر پروتکل در زمان استقرار تأیید شوند.

## ۳) اینتنت نمونه (همان که فاز برای آن ساخته شد)

```text
«با ۰ سرمایه اولیه، هر آربیتراژی که بعد از Gas + Flash Fee حداقل ۰.۵٪ سود دارد اجرا کن»
```

`parseFlashIntent` این جمله (و معادل انگلیسی‌اش) را می‌خواند:

- رقم‌های فارسی/عربی (`۰.۵٪`) نرمال می‌شوند؛
- «سرمایه صفر / بدون سرمایه / zero capital» → `initialCapital: 0`؛
- درصدِ کنار واژه‌های سود/بازده → `minNetProfitBps: 50` (بین ۱ تا ۵۰۰۰ bps مهار می‌شود)؛
- نام زنجیره و دارایی (فارسی/انگلیسی) → `chainId` / `asset`.

## ۴) خط لولهٔ ۹ مرحله‌ای

| # | مرحله | خروجی |
|---|---|---|
| ۱ | جمع‌آوری قیمت | snapshot های reserve از venueها (بیشینه عمر ۱۵ ثانیه) |
| ۲ | یافتن آربیتراژ | همهٔ چرخه‌های دو-venue برای یک جفت‌ارز، رتبه‌بندی بر سود |
| ۳ | حجم بهینه وام | فرم بستهٔ دو-استخر + جست‌وجوی عددی برای N-hop، نتیجهٔ نهایی BigInt |
| ۴ | برآورد گاز | gasUnits × gasPrice × قیمت native |
| ۵ | کارمزد فلش | premium همان provider (Aave ۵bps / Balancer ۰) |
| ۶ | Slippage | minOut برای هر hop با بافر پیش‌فرض ۳۰bps + deadline پیش‌فرض ۶۰ ثانیه |
| ۷ | شبیه‌سازی | **الزامی**؛ بدون simulation هیچ امضایی درخواست نمی‌شود |
| ۸ | گیت ارسال | فقط اگر سود خالص > 0 **و** ≥ حد اینتنت **و** همهٔ گیت‌ها سبز باشند |
| ۹ | صرف‌نظر یا صدور | اگر سود کافی نبود: `NO_TRADE` — اصلاً تراکنشی ساخته نمی‌شود |

فرمول سود خالص:

```text
ناخالص        = خروجی مسیر − (اصل وام + premium)
کارمزد پلتفرم = ۰.۷٪ از ناخالص (هم‌راستا با نرخ سواپ FBT)
حفاظ MEV      = ۱۰bps از ناخالص (پیش‌فرض)
خالص (USD)    = ناخالص − گاز − کارمزد پلتفرم − حفاظ MEV
تصمیم         = خالص > 0 و خالص ≥ حداقل اینتنت  →  ادامه؛  وگرنه  →  NO_TRADE
```

### ریاضی حجم بهینه (دو استخر)

برای دو استخر constant-product با کارمزد `f` و premium فلش `p`، optimum بسته است:

```text
x* = [ γ·√(A₁·A₂·B₁·B₂/(1+p)) − A₁·B₂ ] / (γ·B₂ + γ²·B₁)      γ = (10000−f)/10000
```

- استخرهای هم‌قیمت → `x* = 0` (هیچ حجم سوددهی وجود ندارد).
- برای N-hop از ternary search روی تابع تک‌مودی سود استفاده می‌شود و جواب با
  پالایش عددی روی BigInt تا دقت ~۰.۰۱٪ همگرا می‌شود؛ اسکراپ تست، همگرایی عددی را
  با فرم بسته قفل کرده است.

## ۵) قرارداد مرجع `FlashLiquidityRouter.sol`

- هر دو مسیر Aave (`executeOperation`) و Balancer (`receiveFlashLoan`) پیاده شده‌اند.
- هر hop فقط روی targetهای allowlist اجرا می‌شود؛ خروجی هر hop با delta موجودی و
  `minOut` چک می‌شود؛ گردِ توکن میانی (dust) کل تسویه را abort می‌کند.
- چک on-chain `INSUFFICIENT_PROFIT`: اگر موجودی نهایی < اصل + premium + حداقل سود
  باشد، کل تراکنش revert می‌شود — یعنی «معاملهٔ زیان‌ده تسویه نمی‌شود».
- فقط owner یا executor (کیف پول ربات) شروع می‌کند؛ executor نمی‌تواند allowlist
  عوض کند یا سود را جابه‌جا کند.
- callback فقط از همان source فعال در همان تراکنش پذیرفته می‌شود (`_activeSource`).
- حجم بایت‌کد: ~۱۱.۴KB (زیر سقف ۲۴KB).
- **ممیزی نشده است.** آرتیفکت با `audited: false` باندل می‌شود و متن صریح
  «NOT AUDITED» دارد. قبل از mainnet: ممیزی مستقل + پیکربندی آدرس.

## ۶) API سرور (فقط dry-run)

| مسیر | توضیح |
|---|---|
| `GET /api/flash-liquidity/v1/capabilities` | Providerها، زنجیره‌ها، سقف‌ها، وضعیت استقرار |
| `POST /api/flash-liquidity/v1/scan` | اسکن چرخه‌ها روی snapshot های ورودی (۲ تا ۲۴ عدد) |
| `POST /api/flash-liquidity/v1/plan` | خط لولهٔ کامل روی snapshot ها + policy |

- هیچ کلید، وجه، calldata یا payload امضاشده‌ای قبول نمی‌شود؛ هیچ‌چیز broadcast نمی‌شود.
- ورودی‌ها کراندار (سقف تعداد snapshot، سقف رقم‌ها، سقف گاز/گوی/کارمزد).
- خروجی همیشه `mode: "dry-run"` و `broadcasts: false` را تکرار می‌کند.
- متغیرهای استقرار: `FLASH_LIQUIDITY_ROUTER_ADDRESSES` (مثل `42161:0x...`) و
  `FLASH_LIQUIDITY_ROUTER_AUDITED` (فقط بعد از ممیزی واقعی).

## ۷) صفحهٔ `/#/flash-liquidity`

- اینتنت فارسی/انگلیسی می‌گیرد و تفسیرش را به‌صورت چیپ نشان می‌دهد.
- سه سناریوی **نمونهٔ آموزشی** (سودده / برابر / اسپرد منفی) + ورودی JSON دلخواه.
- اجرای خط لولهٔ ۹ مرحله‌ای کاملاً روی دستگاه (بدون نیاز به سرور) و نمایش گام‌به‌گام ✓/✗.
- جدول حساب‌وکتاب سود با تفکیک گاز / کارمزد پلتفرم / حفاظ MEV.
- برای تصمیم `NO_TRADE` پیام صریح: «معامله‌ای ارسال نشد».
- برای هر حالت می‌توان رسید ساخت (`not-sent` / `reverted`) — اثر انگشت محتواست، نه امضا.

## ۸) چیزهایی که این فاز عمداً انجام نمی‌دهد

- اجرای خودکار/ربات ۲۴-ساعته: نیازمند زیرساخت executor وثیقه‌دار و مانیتورینگ — فاز بعدی.
- اتصال به quoteهای زندهٔ DEX: مسیر اتصال multiVenue موجود به snapshot های on-chain در نقشهٔ راه است.
- چند-دارایی واقعی در صفحه: قرارداد پشتیبانی می‌کند؛ UI فعلاً تک-دارایی آموزشی است.
- دور زدن KYC/تحریم یا هر مسیر CEX: مطابق فازهای قبل، عمداً رد شده.

## ۹) چک‌لیست فعال‌سازی اجرای واقعی (ترتیب الزامی)

1. [ ] آدرس‌های Aave/Balancer زنجیرهٔ هدف از مستندات رسمی تأیید و در رجیستری ثبت شود.
2. [ ] `FlashLiquidityRouter` روی زنجیرهٔ هدف دیپلوی شود (به‌تنهایی یا از طریق owner امن).
3. [ ] ممیزی مستقل قرارداد + انتشار گزارش؛ بعدش `FLASH_LIQUIDITY_ROUTER_AUDITED=true`.
4. [ ] `FLASH_LIQUIDITY_ROUTER_ADDRESSES` تنظیم شود.
5. [ ] شبیه‌سازی (eth_call / bundle) به گیت مرحلهٔ ۷ وصل شود.
6. [ ] مسیر ارسال خصوصی (relay/bundle) تأیید شود — ممپول عمومی همیشه رد است.
7. [ ] اجرای اول فقط با امضای دستی کیف پول و مبلغ آزمایشی انجام شود.

> قانون ثابت: اگر هر چرخ دندهٔ بالا غایب باشد، قابلیت در `planning-only` می‌ماند.
> این شکست نیست؛ همان صداقتی است که بقیهٔ Intent OS را معتبر نگه می‌دارد.
